## 2. Findings by severity

### Medium (High if the Render pipeline service is deployed) — bundled `EXPO_PUBLIC_PIPELINE_API_KEY` is the sole auth for GPU-spend endpoints
Corrected after review — I had first mis-filed this key as a harmless
"Render-side auth value." It is not.

> **Exploit mechanics deliberately not restated here** — the fix is unconfirmed
> and this report is committed to a public repo (same treatment as 1b/1c). At the
> level the fix-owner needs: `EXPO_PUBLIC_PIPELINE_API_KEY` is inlined into the
> shipped app bundle (recoverable with `strings`) and is the **only** thing
> guarding the root Flask service's `/api/mobile/*` job endpoints, whose jobs
> dispatch to the Modal GPU pipeline. So **if that Render service is deployed,
> anyone who pulls the app can drive GPU spend / queue exhaustion against it** and
> reach the other mobile endpoints — no account needed. `clippar_app/CLAUDE.md`
> already records this as a known landmine ("Secret keys ship in the client …
> Move behind an Edge Function proxy"). The endpoint list, request shape and exact
> file:lines were sent to Henry in the private notification.

**Severity is deployment-dependent, and I can't see infra.** The current
shipping app's live processing path is the `process-round` **edge function** →
Modal (JWT- and ownership-checked), and the July 29 audit noted `lib/pipeline.ts`
has no call sites in the shipping app and its Modal credentials pointed at a
since-deleted project — evidence the `app.py` Render path is legacy. **If that
Render service is not deployed, there is no live attack surface today**; the
moment it is (or is redeployed), the bundled key protects nothing. Either way it
should not be called clean.

**Left as-is, reported** — the fix is architectural (put these endpoints behind
an authenticated edge-function proxy or scope them per-user server-side, and
retire the bundled key), exactly the class of change the audit rules say to
describe rather than make unattended. **Recommendation:** confirm whether the
Render service is deployed; if yes, treat the shared key as public and
rotate/retire it and gate those endpoints on the Supabase JWT; if it's dead,
delete the Render service and `lib/pipeline.ts` and drop the bundled key from the
build.

### Low — `sync-courses` admits admins by email match, not just user id
`isAdminUser()` in the `sync-courses` edge function grants admin if the caller's
JWT **email** matches an `admin_users` row, not only if the JWT **user id** does.

> **Risk (detail in the private notification; fix unconfirmed, report committed to
> a public repo):** the admin-gated catalog actions (`approve_suggestion`,
> `sync_region`) become reachable by anyone who can obtain a session whose email
> equals an admin's — which requires email confirmation to be disabled or an
> admin address to be re-registerable. Impact is capped at **shared course-catalog
> tampering** (not tenant data, not payments), hence Low.

**Left as-is, reported.** The safe fix is to drop the email branch and match on
`user_id` only — but I can't see the `admin_users` table, and if its rows are
keyed by email rather than user_id, removing the branch locks out every admin.
This is an authorization path; per the audit rules I won't change it unattended.
**Recommendation:** decide deliberately — either (a) enforce mandatory email
confirmation and keep the branch, or (b) backfill `admin_users.user_id` and drop
the email match. Severity is capped at "catalog tampering", hence Low.

### Low — dormant `redeem-code` edge function is deployable dead code
`clippar_app/supabase/functions/redeem-code/` and its migration
`supabase/retired/018_redemption_codes.sql`. The function was superseded on
2026-08-04 by App Store Offer Codes; the migration is retired (not in the push
path), the tables don't exist in prod, and `app/profile/redeem.tsx` uses the
StoreKit redemption sheet — there is no client call to the function. Its design
was sound (getUser-verified user only, CSPRNG codes, fail-closed rate buckets,
atomic single-UPDATE consumption). Residual risk is only that someone deploys it
by mistake; it would 500 on the missing table.

**Left as-is, reported.** **Recommendation:** delete the `redeem-code` directory,
the retired migration, and the now-unused `REDEMPTION_CODE_PEPPER` secret once
Offer Codes are confirmed working in production. Kept out of this branch to
avoid deleting a whole function unattended.

### Informational — stale rate-limit comments could be "fixed" backwards
`search-courses/index.ts:143` and `get-shared-reel/index.ts:77` still say the
client IP keys on the *last* `X-Forwarded-For` entry. The shared helper
`_shared/rateLimit.ts` was correctly changed to prefer `cf-connecting-ip` then
the *first* entry. The code is right; the comments are stale and describe the
opposite, so a future reader could "correct" the code into a per-request-bucket
bypass. Worth a one-line comment fix next time these files are touched.

## 3. Checked and found clean (so tomorrow doesn't repeat it)

**Committed secrets** — the **working tree is clean**, but the repository as a
whole is **not** (see 1a — this is why the scope note above matters). Beyond that
one object: no
`sk_live`/`whsec_`/`AIzaSy`/`service_role…eyJ`/PEM blocks anywhere in tree or
full history; the `_shared/apple.ts` hits are documentation/regex; `.p8` strings
in tests are locally-generated fixtures. Supabase JWTs in `r.html` decode to
`role:anon` (public by design); the Sentry DSN is a public client DSN. All
tracked `.env.*.example` files contain placeholders only (`YOUR_…`,
`pk_test_…`, `appl_YOUR_…`). No real Stripe/RevenueCat/Shopify/Slack/GitHub/AWS
tokens. Ignore rules cover the usual credential and local-database files by
extension — but they postdate the leaking commit, so they do nothing for the
object already pushed (see 1a). Note ignore rules are themselves world-readable:
they must never name a specific sensitive file, which is a mistake this repo made
and corrected on 2026-08-26.

**Client bundle secrets** — the keys read from `EXPO_PUBLIC_*` /
`constants/config.ts` are the Supabase anon key, Stripe **publishable** key, and
RevenueCat **public** SDK key, all public by design; no service-role or secret
key is inlined. The GolfCourseAPI key was moved server-side. **Exception:**
`EXPO_PUBLIC_PIPELINE_API_KEY` is *not* harmless — it is the sole auth for the
`app.py` GPU-spend endpoints; see the Medium finding in §2. Do not treat it as
clean.

**Row Level Security** — no new tables or migrations since 019, so no new
unpoliced surface. The full table-by-table sweep in `TENANT_ISOLATION_2026-07-31.md`
still holds; I re-confirmed 019 is present in the tree and its `profiles` INSERT
re-grant, `shots` round-ownership WITH CHECK, `clips` storage policies, and
`public=false` force are all as written. (Deployment of 019 is the open question —
see 1a.)

**Edge functions (all 12)** — every user-facing entry point verifies the JWT
server-side with `supabase.auth.getUser(token)` and acts only on the verified id;
none trusts a body-supplied user id. `stripe-webhook` does real
`constructEvent` signature verification and returns a fixed `'Webhook Error'`
string (the July-29 err.message leak is fixed and still fixed).
`revenuecat-webhook` uses constant-time shared-secret comparison, refuses sandbox
events, and requires an allowlisted product id before writing lifetime access.
`get-shared-reel` signs a key **derived from the round id**, so `reel_url` cannot
influence what is signed (the signing-oracle fix holds). `process-round` checks
ownership, claims atomically via the service-role-only `dispatch_claimed_at`, and
no longer sends the service-role key to Modal. All client-callable functions are
rate-limited; no raw `err.message` reaches any caller.

**Injection** — Supabase `ilike('name', '%'+query+'%')` sends the value as a
bound parameter (not string-built into `.or()`); no concatenated `.or()`/`.filter()`
filters exist. Python workers: `db.py` and `modal_detector.py` interpolate only
code-controlled column names, with all values passed as `%s` parameters. The
public waitlist `clippar-web/api/submit.py` is fully parameterized, body-capped
(4 KB), format/length-validated, honeypotted, and rate-limited fail-closed
per-IP and globally.

**Insecure storage** — the Supabase session (with the long-lived refresh token)
is stored only in `expo-secure-store` (Keychain, `…ThisDeviceOnly`) on native;
the in-memory mirror never persists to disk, and legacy AsyncStorage sessions are
purged on launch. No token or secret is written to AsyncStorage.

**Storefront / web** — `clippar-web` ships a strict CSP (`default-src 'self'`,
`object-src 'none'`, `frame-ancestors 'none'`), plus HSTS, `X-Frame-Options:
DENY`, `nosniff`, a locked-down `Permissions-Policy`, and `Referrer-Policy`. The
public shared-reel viewer `public/r.html` renders every attacker-controlled field
via `textContent` / `createElement` — never `innerHTML` — and encodes the share
token into the request. No XSS sink, no token exposed in theme assets.

**Dependencies** — `npm audit --omit=dev` flags high-severity advisories in
`@babel/core`, `@xmldom/xmldom`, `brace-expansion`, `fast-uri`, `image-size`,
`metro`, `@expo/metro`. **All are build-time bundler/toolchain packages** — none
ships in the app bundle or runs in the edge-function (Deno) runtime, and every
advisory requires feeding malicious input to the bundler at build time (i.e. the
attacker already controls the build). None is runtime-reachable by an external
attacker, so none is a real finding. Worth a routine `npm audit fix` for hygiene
when convenient, but not security-urgent.
