## Findings by severity

### HIGH (correctness) — the reel's scorecard is wrong on ordinary rounds — FIXED

Yesterday's PR #142 fixed one cause of the scorecard sitting over the wrong shots: clips
dropped as unrecoverable were still counted into the hole boundaries. That fix is right.
But the same timeline has a **second, much more common** source of the same error, and
PR #142 preserved it — its new `holeReelDurationMs` doc comment explicitly says the value
it uses is "now correctly written by markClipTrimmed", which is true of SQLite and false
of the value the function actually reads.

`useEditorState`'s auto-trim (`processAllUntrimmed` → `processOneClip`,
`hooks/useEditorState.ts:905-928`, and the same block in `trimClip`, `:664-678`) builds

```ts
const updatedClip: EditorClip = { ...clip, needsTrim: false, autoTrimmed: true };
…
updatedClip.sourceUri  = result.trimmedUri;   // now the TRIM file
updatedClip.originalUri = originalSourceUri;
updatedClip.trimStartMs = result.trimStartMs; // original-timeline bounds
updatedClip.trimEndMs   = result.trimEndMs;
```

`durationMs` is never reassigned, so it stays the **untrimmed recording's** length while
`sourceUri` points at a file a fraction of that long. SQLite gets the corrected number
(`markClipTrimmed` writes `duration_seconds = (autoTrimEndMs - autoTrimStartMs)/1000`, and
its own comment says why: *"Without this update … downstream code thinks the clip is much
longer than it actually is"*). React state never re-reads it. `updateClipDuration` exists
in the hook for exactly this and has **zero call sites**.

Nothing reloads the editor in between: `processAllUntrimmed` fires on mount
(`app/round/editor.tsx:602-609`) and `editor.reload()` only runs on a *re*-focus
(`:570-579`). Export un-greys the moment `needsTrim` clears. So the session that trims the
clips is the session that exports them, and in that session every auto-trimmed clip
reports the wrong length.

**Concrete failure.** A golfer finishes 9 holes, 18 clips, each recorded ~30s and
auto-trimmed to ~3s. They open the editor, watch the trim run, and tap Export without
leaving the screen. The scorecard payload says hole 1 spans 0–60s; the reel it is drawn
over is 6s long. Native picks each shot's card by matching its position against those
ranges (`fastGroupSegments`, `ShotDetectorModule.swift:2300`), so **every shot after the
first carries hole 1's scorecard** and the card never advances. The export reports success.

It survived because the in-app preview card is driven by the currently-playing clip's own
`holeNumber` (`app/round/preview.tsx:129-139`), not by a timeline — so the preview looks
right and only the exported file is wrong. Henry's rule is "the same scorecard that's on
the preview is the exact same I want on the export reel"; this is the one place they can
disagree without anything erroring.

**Second, smaller instance of the same class, also fixed.** For a clip that was *not*
pre-trimmed, the old arithmetic read `trimEndMs === -1` as "count the whole file" and
dropped `trimStartMs` on the floor. `-1` means "play to the end", not "ignore the start
handle" — native plays `[trimStartMs, end)` (`fastParseClips`, `:2266-2269`). A user who
drags only the start handle in by 2s (`ClipTrimModal.handleSave` writes exactly
`finalStart > 0, finalEnd = -1`) pushed every later hole 2s late.

**Fix** (`clippar_app/lib/reelScorecard.ts`). `holeReelDurationMs` now derives each clip's
contribution from the same split `composeClips` uses when it tells native what to play,
instead of trusting a cached field:

- pre-trimmed → the **width** of the trim window (`trimEndMs - trimStartMs`), which is the
  trim file's length by construction and is precisely the number `markClipTrimmed`
  persists; `durationMs` only as the fallback when there is no explicit end;
- otherwise → `(trimEndMs === -1 ? durationMs : trimEndMs) - trimStartMs`.

Four new tests, including an end-to-end one that pins hole 2's boundary for an auto-trimmed
round. All four fail against the pre-fix function and pass after. **531 tests pass, `tsc
--noEmit` clean.**

**The root cause is deliberately left alone.** The one-line fix at source is to add

```ts
updatedClip.durationMs = Math.max(0, result.trimEndMs - result.trimStartMs);
```

to both auto-trim branches in `hooks/useEditorState.ts`, which would make React state agree
with what is already written to SQLite. I did not apply it: `durationMs` also feeds the
trim UI (`getInitialTrimBounds` switches between original-timeline and source-timeline mode
on it, `types/editor.ts:78-104`; `preview.tsx:1201` passes it to the native player), and
that is native-only rendering I cannot see here. Correcting it moves the trim modal from one
supported mode to the other, which changes where the handles open. **That is a change that
wants eyes on a device**, and the reel fix above does not depend on it — it no longer reads
the stale field at all. Worth doing next time that screen is open on hardware; it would also
retire the dead `updateClipDuration`.

### MEDIUM (correctness) — yesterday's Swift compose bug is in TWO functions, not one — NOT FIXED, needs a device

The 08-23 report named `composeReelOnDevice`'s legacy path
(`ShotDetectorModule.swift:2824`): a clip whose video track will not parse inserts nothing,
but `:2864` still advances the composition cursor by its full trim duration, so the reel
gets a silent black gap; and `renderSize` comes from `index == 0` (`:2832`) rather than the
first clip actually inserted, so if clip 0 is the skipped one the whole reel renders at the
default 1080×1920.

**`stitchClipsOnDevice` has the identical defect** — `:1583` (no `else` on the video-track
binding), `:1591` (`if index == 0` for `renderSize`), `:1629` (cursor advanced regardless).
That is the function behind per-hole save/share and multi-select export, i.e. a completely
separate user-facing flow. A fix applied only where yesterday's report pointed would leave
half the bug in place.

The fast path already gets this right and is the model for both:
`fastExportSegment:2375` does `guard let srcVideo = … else { continue }` **before** the
cursor advances at `:2396`.

Still not patched here, deliberately — video export, hardware-dependent, not CI-catchable,
standing rule holds. **Needs Henry on a device with a real export.**

### LOW (robustness) — export status is only checked for `.failed` — NOT FIXED, unchanged

`trimVideoPassthrough:262-270` and `detectAndTrimVideo:459-467` capture
`exportSession.error` only when `status == .failed`, so a `.cancelled` session resolves
**successfully** with a `trimmedUri` pointing at a file that was never written. Every other
export in the file guards on `status == .completed`. Nothing calls `cancelExport()`, so
there is still no live trigger and I am not claiming one. Unchanged from 08-23; align it
next time that code is open.

## Security posture — clean, nothing new

- **Secrets.** No service-role JWT, Stripe secret, private-key PEM, AWS or GitHub token in
  the working tree. The two `eyJ…` strings in `clippar-web/public/r.html` are `role:anon`
  keys, which are meant to be public. Added-then-deleted scan across all August history:
  nothing. Every edge function reads its key from `Deno.env`.
- **RLS.** Re-resolved the `CREATE`/`DROP POLICY` chain across 001→019 in order. The
  permissive policies are all genuinely dropped: `courses`/`holes` global UPDATE (007) by
  013, bucket-wide `clips` storage (008/011) by 017 and 019, public `rounds` SELECT (001) by
  013. `apple_credentials` has RLS on and no policy at all — service-role only, correct.
  `processing_jobs`, `daily_usage`, `course_suggestions` expose SELECT-own and nothing else.
  No table where user A can reach user B's rows.
- **Column grants checked in migration order**, which the earlier audits did not: 013
  `REVOKE UPDATE ON rounds` then re-grants a column list, and 015 additively grants
  `UPDATE (start_hole)`. 019 does not revoke `rounds` again, so the tee-off-on-10 feature
  (#135) still has its write. No silent breakage.
- **Edge functions.** All 11 entry points verify the caller: 8 via `auth.getUser(token)`
  against the auth server, `stripe-webhook` via `constructEvent`, `revenuecat-webhook` via a
  configured shared secret, `get-shared-reel` unauthenticated by design with an IP rate limit
  keyed on the *last* X-Forwarded-For entry. None trusts a client-supplied user id.
- **Client.** Auth tokens in expo-secure-store. No injection into `.ilike()`/`.or()`.
  `safeRegionCode` still allowlists the one caller-supplied value that reaches the upstream
  query string.
