## Findings by severity

### HIGH (correctness) — the reel's scorecard can sit over the wrong shots — FIXED

`app/round/editor.tsx` built the reel's per-hole timeline from **every non-excluded clip**,
but composed the reel from a **smaller list** — the clips whose file still exists on disk,
or could be re-downloaded from Supabase. Clips that are missing locally and cannot be
recovered are dropped, and the UI even says so ("2 clips unrecoverable — skipping…").
Their durations were still counted into the scorecard's hole boundaries.

Native picks which hole's card to draw over a shot by matching that shot's position in the
reel against those boundaries (`fastGroupSegments`, and the CALayer fade times on the
legacy path). So every boundary after a dropped clip sat later than the video really was.

**Concrete failure.** A golfer plays nine holes. Two clips on hole 1 were uploaded, then
iOS evicted the local files — an ordinary event, which is exactly why the recovery path
exists — and the re-download fails on course Wi‑Fi. The editor drops them (8s of footage),
composes, and from that point every shot in the reel carries a card from an earlier hole,
the offset never corrects, and nothing errors. The reel looks finished and is wrong.

**Fix.** The per-hole duration arithmetic moved into a pure, tested
`holeReelDurationMs(clips, isInReel)` in `lib/reelScorecard.ts`, and the editor now passes
the set of clips that actually reached the composer. Six unit tests cover the dropped
clip, excluded clips, user trims, pre-trimmed clips, and negative bounds; one more asserts
the corrected hole boundaries end-to-end.

### MEDIUM (correctness) — a user's trims could be silently discarded — FIXED

Same file, same flow. `composeClips` re-derived which `EditorClip` produced each surviving
URI by **string-matching the URI back against the clip list**, guessing at recovered files
with `uri.includes(`${clip.id}.mp4`)`. On any miss the cursor ran off the end of the array
and every remaining clip fell to the `?? 0` / `?? -1` defaults — i.e. **full source clip,
user's trim thrown away**, for the whole rest of the reel, silently.

The pairing was already known by index at the point the drop decision is made; the walk was
reconstructing information it had just discarded. The clip is now carried alongside its URI
(`validClips[i]` ↔ `validClipUris[i]`), and the walk is gone. This also removes the
recovery flow's duplicated rebuild branch — the two cases collapse to one expression.

Both fixes are in one PR: **`CTO review — 2026-08-23`**, branch `cto/2026-08-23`.

### MEDIUM (correctness) — legacy reel compose silently drops a clip — NOT FIXED, needs a device

`composeReelOnDevice`'s legacy path (`ShotDetectorModule.swift:2824`) inserts a clip's video
only `if let assetVideoTrack = asset.tracks(withMediaType: .video).first`. When that is nil
there is no `else` — but line 2864 **still advances the composition cursor by the clip's full
trim duration**. The clip's frames are missing and the timeline is padded with a gap.

The trigger is the fast path's own guard. `fastParseClips` (line 2262) *throws* on a clip
with no video track; the caller treats that as "fast path failed" and falls back to legacy.
So the one input the fast path refuses is handed straight to the path that mishandles it.

**Concrete failure.** A recording is interrupted (call, force-quit, storage full) and leaves
a file whose video track will not parse. Compose falls back to legacy. The finished reel
contains a black gap where that shot should be, the reported duration includes it, and the
export reports success.

There is a second half. `renderSize` is taken from `index == 0` (line 2832) rather than the
first clip actually inserted. The fast path deliberately uses "first usable clip"
(`if parsed.isEmpty`, line 2272) and its comment claims the legacy loop matches it "exactly"
— it does not. If clip 0 is the one skipped, or is trimmed to zero length (line 2818), the
entire reel renders at the default **1080×1920 portrait** regardless of the real footage, and
`computeFillTransform` then crops or letterboxes every shot in it.

**Not fixed, deliberately.** This is the video-export path, it is hardware-dependent, and
CI cannot catch a regression here — the standing rule against speculative Swift changes
applies. The fix is small and I'd suggest it as: `guard let assetVideoTrack = … else
{ continue }` before the insert, so a clip with no video track advances nothing; and bind
`renderSize` to `clipSegments.isEmpty` rather than `index == 0`, matching the fast path.
**Needs Henry to apply and confirm on a device with a real reel export.**

### LOW (robustness) — export status is only checked for `.failed` — NOT FIXED

`trimVideoPassthrough` (line 264) and `detectAndTrimVideo` (line 460) capture
`exportSession.error` only when `status == .failed`. A `.cancelled` session leaves
`exportError` nil, so both resolve **successfully** with a `trimmedUri` pointing at a file
that was never written. `stitchClipsOnDevice`'s passthrough path and every helper in the
fast compose path already do the right thing (`guard session.status == .completed`).

Nothing in the app calls `cancelExport()`, so I could not construct a live trigger for this
and am **not** claiming one — it is an inconsistency with the rest of the file, in the
direction of "reports success, produced nothing". Worth aligning the next time that code is
open on a device.

## Security posture — clean, nothing new

- **Secrets.** No service-role JWT, Stripe secret, SMTP password, AWS key or private-key PEM
  in the working tree. Full-history scan for added-then-deleted secrets returns only
  placeholders (`YOUR_DEV_SERVICE_ROLE_KEY`, `test-key`) and the already-closed
  GolfCourseAPI key. Every edge function reads its key from `Deno.env`, none inline one.
- **RLS.** All 16 tables have RLS enabled. I re-resolved the full `CREATE`/`DROP POLICY`
  chain across 001→019 in order rather than reading the final files: the permissive
  policies are all genuinely dropped — `courses`/`holes` global UPDATE (007) dropped by 013,
  bucket-wide `clips` storage access (008/011) dropped by 017 and 019, and the public
  `rounds` SELECT dropped by 013. Nothing left where user A can read or write user B's rows.
  Authenticated INSERT on `courses`/`holes` survives and is a documented decision (013:78-86,
  the `sync-courses` upsert path), rate-limited per user per day.
- **Edge functions.** All 11 entry points verify the caller: 8 via `auth.getUser(token)`
  against the auth server, `stripe-webhook` via `constructEvent` signature,
  `revenuecat-webhook` via a configured shared secret, `get-shared-reel` unauthenticated by
  design with an IP rate limit keyed on the *last* X-Forwarded-For entry. None trusts a
  client-supplied user id. `get-shared-reel` derives the storage key from the round id
  rather than the client-writable `reel_url` — the signing-oracle hole is structurally
  closed, not just guarded.
- **Client.** Auth tokens in expo-secure-store, not AsyncStorage. No injection into
  `.ilike()`/`.or()` filters. `persistAsset` rejects `/`, `\`, `.` and `..` in filenames at
  the sink.

One note, explicitly **not** a finding: `resolveFileURL` (line 588) force-unwraps
`URL(string: uri)!`, which would be a hard crash rather than a rejected promise on a URI
`URL(string:)` cannot parse. I traced the callers — every URI reaching it is built by the
app from a round UUID or row id plus `Date.now()`, and `persistAsset` guards the one place
a string becomes a path. **There is no live crash path**, so it is listed here as a
one-line hardening opportunity, not a bug.

## Android — the honest estimate

Henry ranks Android second and no date has been quoted. Here is the number that decides it.

**The two native modules are ~6,300 lines of Swift with no Android counterpart:**
`shot-detector` (5,470 lines) and `swing-vision` (835). They lean on Vision, AVFoundation,
CoreML, Accelerate/vDSP, CoreMotion and CALayer. Two of those have no equivalent on Android
at all:

- **`VNDetectTrajectoriesRequest`** (ball-launch detection, the shot tracer). Android has
  nothing like it. Building a replacement is real computer-vision work, not a port.
- **`AVVideoCompositionCoreAnimationTool` + CALayer** — the scorecard burned into the reel,
  26 layer call sites. Android has to redraw all of it against Media3's overlay API.

The rest is rewrite-with-a-known-target: body pose goes to ML Kit or MediaPipe (different
joints, different coordinate convention, different confidence scale — **the swing state
machine's thresholds are tuned to Vision's output and would have to be re-tuned against real
Android footage, not translated**); the AVFoundation trim/stitch/export surface (16 export
sessions, 14 compositions) goes to Media3 Transformer; the vDSP audio transient detector
becomes plain Kotlin; the CoreML MobileCLIP model needs re-exporting to TFLite.

**So: Android is a rebuild of the detector and the reel pipeline, not a port.** The
Expo/React Native app above them — screens, routing, Supabase, hooks — does largely carry
over, and that is roughly 20% of the work.

Realistic solo effort, assuming Henry is also doing everything else:

| Piece | Estimate |
|---|---|
| Pose detection + swing state machine re-tuned on Android footage | 3–4 weeks |
| Trim / stitch / compose / export on Media3 | 3–4 weeks |
| Scorecard overlay rebuilt | 1–2 weeks |
| Audio transient detection (vDSP → Kotlin) | 3–5 days |
| swing-vision CoreML → TFLite | 1–2 weeks |
| Shot tracer (`VNDetectTrajectories` replacement) | 3–4 weeks |
| RN shell, Play Billing via RevenueCat, permissions, listing | 2–3 weeks |
| Device-matrix testing (codec/HDR/orientation fragmentation) | 2–3 weeks |

**4–6 months** for parity. **3–4 months** if the shot tracer is cut from Android v1 —
which I would recommend, because it is already shipped behind a kill switch
(`config.tracer.enabled`) and is off. That is the single biggest lever on the date.

This is an estimate from reading the code, not from a spike. Treat the ranges as ranges. If
a date has to be committed before then, the cheapest way to firm it up is a two-week spike
on pose detection alone — that one piece decides whether the whole thing is a rebuild or a
disaster.

## Deliberately not touched

- **`ShotDetectorModule.swift`** — the two findings above are described, not patched.
  Hardware-dependent, not CI-catchable, standing rule holds.
- **Authentication, Stripe, RevenueCat** — not touched.
- **The legacy pipeline path** (`lib/r2.ts`, `lib/pipeline.ts`) — retiring it or proxying the
  key is Henry's product call, unchanged for three runs now.
- **The dead intro/outro slot in the reel.** `getAllClipsInOrder` prepends `state.intro` and
  appends `state.outro`, and neither contributes to the scorecard timeline — so an intro
  clip would offset the entire reel's card by its own length. `setIntro`/`setOutro` have
  zero call sites and both are null for the life of the screen, so **this is not live** and
  I did not "fix" it. It is a trap for whoever builds that feature; the note belongs in the
  code, and the fix at that point is to include intro/outro in the timeline.
