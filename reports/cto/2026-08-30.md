## Part 1 — Correctness

### 1. HIGH — a user-typed course name could delete that round, permanently

`lib/tutorialRound.ts`. `sweepTutorialRounds()` selected rounds to destroy by course
name:

```ts
const orphans = await getOrphanedRounds().catch(() => []);
for (const o of orphans) if (o.course_name === TUTORIAL_COURSE_NAME) candidates.add(o.id);
```

`TUTORIAL_COURSE_NAME` is the string `'Tutorial round'`, and `course_name` is free text —
`app/(tabs)/record.tsx:1535` binds a `TextInput` straight to it via
`onChangeText={setCourseName}`.

**The failure, concretely.** A golfer types "Tutorial round" as the course on the
round-setup screen and plays it. `getOrphanedRounds()` returns it (it is `in_progress`
and owned by them), the name matches the sentinel, and the guard on the next line
(`if (row && row.course_name !== TUTORIAL_COURSE_NAME) continue`) passes it through
because the name genuinely does match. `deleteLocalRound(id)` then drops the local rows
and unlinks every clip file, and `deleteRound(id)` deletes the remote row. **The round
and every video in it are gone, on the phone and on the server. Nothing is written to
the recently-deleted bin and there is no undo.**

It runs on every authed app start — `app/_layout.tsx:114`, `if (!active) void
sweepTutorialRounds()` — with no feature-flag gate. So although v3 onboarding is still
off by default, the sweep that serves it is live for every user the moment this branch
merges.

Likelihood is low: it needs that exact string. Consequence is total and irreversible, and
the trigger is entirely in the user's hands.

**Fix.** A sentinel the user can type is not a sentinel. Candidates now come from an id
registry — `tutorial.created_round_ids`, written by `createTutorialRound` immediately
after the round is created — so only rounds this app created as tutorial rounds are ever
eligible. The `getOrphanedRounds()` scan is gone. The course-name comparison is kept
underneath as a second gate rather than as the only one, and swept ids are pruned so the
registry does not grow for the life of the install.

Cost of the change: if the app dies in the window between `createRound` returning and the
registry write completing, that tutorial round survives as clutter in the user's history
instead of being collected. Leaving clutter is the right side of this trade.

### 2. MEDIUM — two overlapping deletes could lose a clip the UI promised was recoverable

`lib/clipBin.ts`. All three mutations were read-modify-write over one `local_settings`
row. `getSetting`/`setSetting` are a bare `SELECT` and a bare `INSERT OR REPLACE` — no
transaction, no compare-and-swap, no row lock.

**The failure, concretely.** `deleteClipToBin` removes the clip row from SQLite *first*
and records the recovery entry *second*. Two of those overlapping: both read the same bin
array, both write; the second write was computed from a snapshot taken before the first
landed, so the first clip's entry is dropped. That clip is now deleted from SQLite with
nothing to restore it from — while the confirmation dialog has just told the golfer "You
can put it back from Profile → Recently deleted."

`useEditorState.removeClip` fires this deliberately without awaiting ("to keep the tap
responsive"), which is what makes overlap possible at all.

Honest on likelihood: both delete affordances in the editor confirm through an
`Alert` first, and there is no bulk-delete path, so consecutive taps are realistically
hundreds of milliseconds apart against a window of a few DB round-trips. This is a
narrow race, not a routine one. It is fixed because it is cheap to fix and the promise
in the dialog should hold unconditionally.

**Fix.** New `lib/serialQueue.ts` — a promise-chain queue that makes "read, decide,
write" atomic with respect to other work on the same instance. All three bin mutations
run through it. A rejected job settles the tail so one failure cannot wedge the queue.

The test for this is behavioural, not a source grep: it drives an unserialised
read-modify-write against a fake store and asserts that it *does* lose an entry, then
asserts the queued version does not.

### 3. MEDIUM — a failed bin write left the clip unrecoverable

Same function, different path. `deleteLocalClip` had already removed the row when
`writeBin` ran; if that write threw (storage pressure being the obvious cause), the row
was gone and no bin entry existed. `removeClip`'s `.catch(() => {})` swallowed it, so the
golfer saw the clip disappear and nothing else.

**Fix.** The bin write is wrapped; on failure the row is restored with
`restoreLocalClip(row)` and the error is rethrown. The clip then reappears on the
editor's next focus reload — the same visible outcome as the bug this whole feature
replaced, and strictly better than losing the shot.

### 4. LOW — practice clips are labelled as holes in Recently deleted (not fixed)

`app/profile/deleted-clips.tsx` prints `Hole {hole_number} · shot {shot_number}`. In a
training session `hole_number` is a club index (`lib/training.ts` `CLUBS`), so a deleted
7-iron shot shows as "Hole 8 · shot 3". The editor is careful about this everywhere
else — `trainingHoleLabel()` exists for exactly this — but the bin screen predates the
mapping.

Not fixed: the entry carries `roundId`, so the screen would need an async lookup against
the training registry per row, and I would rather Henry decide whether that is worth the
extra read than have me add one on my own judgement. Cosmetic, no data at risk.

## Part 2 — Security

**Nothing new.** The branch touches no migration, no edge function and no auth path.

1. **Committed secrets — clean.** `scripts/secret-scan.sh` over the full unshallowed
   history: `secret scan CLEAN`, exit 0. Tracked dotenv files, live credential shapes,
   opaque binaries, non-production endpoints, unpinned remote imports — all clear.
   **No credential needs rotating.**
2. **Row Level Security — unchanged and intact from source.** No new migration (highest
   is still `019_tenant_isolation.sql`). 16 tables carry `ENABLE ROW LEVEL SECURITY`, and
   no policy in any migration uses `USING (true)`, `WITH CHECK (true)` or `TO public`.
   Per `clippar_app/CLAUDE.md` this is a source read, not a statement about production —
   a checkout cannot tell you what is deployed.
3. **Edge functions.** Two of twelve are intentionally public and both are hardened:
   `stripe-webhook` verifies `constructEvent` against `STRIPE_WEBHOOK_SECRET` before
   doing anything, and `get-shared-reel` requires a 128-bit share token plus
   `is_published = true`, is rate-limited before the token is even read, and returns a
   uniform "not available" so it cannot be used to probe which tokens exist. The other
   ten resolve identity from the verified JWT via `supabase.auth.getUser(token)`. None
   derives identity from a client-supplied user id.
4. **Client-side secrets / injection.** No change on this branch. The existing test
   "SQL still uses bound parameters, never string interpolation" passes.

### Carried findings, re-verified rather than taken on trust

- **Legacy Flask service — worse than this report first stated, and deliberately
  under-described.** The retired Flask service at the repo root takes three credentials
  from the environment with hardcoded literal fallbacks — one of them the Flask
  session-signing key, which matters more than the admin password does. Last touched
  6 April 2026, not referenced by any workflow, but the root `Dockerfile` builds and
  runs it, so an unconfigured deploy would come up using published values.

  **The details stop there on purpose.** I confirmed via the API that this repository is
  public (`"visibility": "public"`), and an earlier draft of this section spelled out the
  exact lines, the exploitation chain and the deployment path. Redacting the literal
  values — which is all the first correction did — bought nothing, because they sit a few
  lines away in the same public tree. What actually raised the exposure was the
  *synthesis*, and that is now removed. Henry can read the three lines; a passer-by gains
  less from the finding than they did an hour ago.

  **This is the real constraint, and it should be named:** an audit report committed to a
  public repository cannot describe an unfixed weakness in that same repository without
  advertising it. Redaction does not resolve that — only closing the finding does. So
  this is escalated rather than documented.

  **Not fixed here, deliberately.** The correct fix is to fail closed — take all three
  from the environment with no default, so an unconfigured deploy refuses to boot — plus
  a constant-time password comparison. That is authentication code, which my standing
  instruction says I do not rewrite on my own judgement, and it belongs to a service
  unrelated to this PR's diff. If the service is genuinely dead, deleting it and its
  Dockerfile closes the finding outright and is the cleaner option. **Henry's call, and
  it is now on his list rather than buried here.** If that host was ever reachable,
  rotate all three values.
- **`sync-courses` admin-by-email.** `isAdminUser(user.id, user.email)` checks
  `admin_users` by `user_id` and, failing that, by `email` — so an account's privilege
  follows its email address. Exploiting it requires passing Supabase's confirmation on
  the new address, i.e. controlling the admin's inbox, at which point the account is
  already lost. Genuinely inert today; the defect is that it widens "admin" from an
  account id to an inbox. Open and undecided since 20 Aug.

## What the review caught that I did not

Worth recording plainly, because it is the most useful thing in this report. Four
findings came from the automated reviewers on PR #152, and one of them is a real
cross-account data-destruction path sitting in a diff I had already reviewed and
described as clean.

### 7. The clip bin was device-wide (Medium — fixed, `cbad128`)

`BIN_KEY = 'clips.bin.v1'` is one `local_settings` row, and `local_settings` is
`(key TEXT PRIMARY KEY, value TEXT NOT NULL)` — no owner column. `listBinnedClips()`
applied no ownership filter, and the Recently-deleted screen calls it with no round id.

**The failure:** one `clippar.db` is shared by every account that signs in on a handset,
and sign-out deliberately does not wipe it. User A deletes shots; the bin keeps the rows
*and the video files*. A signs out, B signs in. B opens Profile → Recently deleted and
sees A's shots. "Delete for good" unlinks A's video files; "Put back" reinserts A's row
under B's session.

What makes this bad rather than theoretical: `lib/localScope.ts` exists *specifically* to
close this exact scenario, and documents it in its header — A leaves a round in progress,
signs out, hands the phone over, and B's `getOrphanedRounds()` used to hydrate A's
footage into B's session. The bin walked straight past a defence this codebase had
already built and paid for.

**Fixed** by keying the bin per account — `clips.bin.v1.<userId>`, the same convention
`pro.status_cache.<userId>` already established — failing closed when no session
resolves, and refusing the delete outright rather than removing a row it cannot record.

### 8. Binned videos survived the explicit "remove my videos" (Medium — fixed)

Same root cause. `removeLocalMediaForCurrentUser` walks rounds through
`deleteLocalRound`, but a binned clip no longer *has* a `local_clips` row — so up to 30
videos survived the one action whose entire purpose is removing them, and survived
sign-out. `clearLocalDatabase` likewise dropped only the Pro cache from `local_settings`.
Both now handle the bin.

### 9. The tutorial id registry had the same shape (Low — fixed, `a634fb8`)

My own fix for finding 1 introduced this. `getLocalRound` is scoped and fails closed, so
under account B a round of A's reads as `null` — which my "a missing local row is
expected" comment waves through — while `deleteLocalRound` is *not* scoped and deletes by
`round_id` alone. Entries now carry their owner; only the signed-in account's are
candidates; other accounts' entries are preserved so their rounds are still collected
later. Bounded impact (tutorial rounds hold bundled demo clips), fixed because this PR is
what made the registry the sole record.

### 10. This report quoted a credential (Low — fixed)

The first draft reproduced `app.py`'s `ADMIN_PASSWORD` fallback verbatim, in a document
written to be circulated, while noting in the same section that the repo is public. The
value was already in the tree so nothing new leaked, but it was a second copy for no
gain — `scripts/secret-scan.sh` argues exactly this about its own output and I failed to
apply it to my own prose. Redacted to a line reference, and
`tests/reportsCarryNoSecrets.test.ts` now derives the literals *from `app.py`* and
asserts no report contains them.

The same finding surfaced the `app.py:25` hardcoded Flask `secret_key`, which I had
missed and which is worse than the password: a known signing key means forging the admin
cookie directly, so the password never matters. Finding 5 is re-rated above.

### The lesson

The review found these in the same file I had just reviewed. My pass was focused on the
*new* code's own logic — races, rollback, retry — and I checked account scoping nowhere,
even though `localScope.ts` is a documented, deliberate invariant in this codebase and
every new `local_settings` key is a chance to break it. **A new `local_settings` key is a
scoping decision.** When the diff adds one, ask who owns it before asking whether it
works.

### Findings 13-16, and where I stopped

Four review rounds ran on this PR, and **every one found something in the previous
round's fix.** That is worth recording as honestly as the original miss:

- **13 (Medium, fixed).** I gated the training reads and the import write and left live
  capture open. `app/training/record.tsx` took `roundId` from the URL, `app.config.js`
  registers a URL scheme so the route is externally reachable, and `useCamera`'s save
  path is a bare `saveLocalClip({ round_id })` with no ownership predicate. Worse, my own
  read-gating made the failure *silent*: the shot counter reads zero, so it looks like a
  fresh session rather than an error. This is the same "one of two routes protected"
  mistake I had criticised in finding 11, made again one file over.
- **14 (Medium, fixed).** My legacy-bin drain from finding 7's fix purged the *whole*
  device-wide list, on my assertion that its entries "cannot be attributed to an
  account" — which would have unlinked the other account's videos, recreating the bug it
  was fixing. They can be attributed: only the clip row was deleted, the round row
  survives, and `getLocalRound` is scoped. **Second time in this PR I reasoned about
  ownership instead of verifying it.**
- **15 (Medium, fixed).** `deleteClipToBin` scoped the bin key but never checked the clip
  was ours. `deleteLocalClip` is `DELETE ... WHERE id = ?` with no ownership predicate
  and ids are small integers, so "callers gate upstream" was a property of today's call
  sites, not the function.
- **16 (Low, fixed).** `restoreLocalClip` interpolates `Object.keys(row)` into SQL
  unescaped, justified by a docstring saying the keys come from the database. This
  feature broke that invariant by round-tripping the row through JSON, and nothing
  recorded it. Validated at the boundary — by identifier *shape*, not an allow-list,
  because `local_clips` has 25 columns added by `ALTER TABLE` and a list would drift and
  silently refuse valid restores.

**I stopped after round 4.** The findings were converging in severity, but each round
still surfaced something in the last one's fix, and that is the point to hand over rather
than keep iterating. Everything still open is listed under "Needs Henry" — item 3 is the
one that matters, because unlike everything fixed here it is **already live**.

### 11. Applying that lesson found the worst one — practice footage (High — fixed, `2013957`)

The branch adds three device-wide `local_settings` keys, not one. Checking the others
against the same question found this, and it is more severe than the bin finding that
prompted the check: it exposes the **footage itself**, not metadata plus a destroy
button.

`training.sessions.v1` is device-wide, and `getClipsForRound` is a bare
`SELECT * FROM local_clips WHERE round_id = ?` with no ownership predicate.

**The failure, verified link by link rather than inferred:** A does range practice on
their phone. A signs out, B signs in. B opens Practice — `listTrainingSessions()` returns
A's sessions from the shared registry, and `trainingShotCounts()` returns A's true
per-club counts, so B sees "Dr ×12 · 7i ×8" for a session they never recorded. B taps
**Watch** → `app/training/play.tsx:67` calls `listTrainingClips(roundId)` → unscoped read
→ **B watches A's swing videos.**

The revealing detail is that the *editor* route off that same screen
(`index.tsx:258`) was already safe: `useEditorState.loadFromLocal` gates on
`getLocalRound`, which is scoped and fails closed, so B gets an error state. The player
simply never had that gate. One of two routes off one screen was protected — which is
exactly the argument for putting the check at the data layer instead of in a screen.

**Fixed** by gating `listTrainingSessions`, `listTrainingClips`, `trainingShotCounts` and
`importShotsToSession` on `getLocalRound` returning non-null. Deciding ownership from the
database rather than from the settings blob also covers registry entries written before
the check existed, with no migration and no shape change.

Not introduced by this PR — it is the trainee-mode code from the branch under review —
but finding it is what this run is for.

### 12. HIGH — account deletion destroys the other account's videos (out of diff, NOT fixed)

Surfaced as a passing observation in the review and verified here, because it is the same
class again and it is worse than most of what is above.

`wipeLocalUserData` (account deletion) does two things in sequence. First
`clearLocalDatabase`, which is **carefully scoped per user** — its own comment explains
that account A deleting their account must not destroy account B's footage, and every one
of its deletes joins through `user_id`. Then, immediately after, `removeOwnedMediaDirectories()`:

```ts
const OWNED_MEDIA_DIRS = ['clips/', 'exports/'];
await FS.deleteAsync(`${root}${dir}`, { idempotent: true });
```

That is the **whole** `documentDirectory/clips/` tree, with no ownership filter at all.

**The failure:** shared handset, A and B have both used the app. A deletes their account.
A's rows go, correctly scoped. Then every video file on the device goes — including B's.
B's SQLite rows survive, now pointing at files that no longer exist, so B opens their
rounds to a library of broken clips. The scoping immediately above is undone by the line
immediately below it.

**Not fixed, deliberately, and this is the one I most want a second opinion on.** It is
outside this PR's diff, it is account-deletion semantics — irreversible by design — and
the minimal correct fix is not a one-liner: the per-row unlink inside `clearLocalDatabase`
already handles the departing user's own files, so the directory sweep exists to catch
*orphans*, and making it safe means deleting only files no surviving row references rather
than dropping the tree. That is a real change to a destructive path, and I would rather
Henry saw the reasoning than have me guess at it inside a review PR.

Filed to `BACKLOG.md` and raised on Henry's list.
