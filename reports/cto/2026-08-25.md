## 2. Security findings

### 2a. HIGH (process) — the CI secret gate could not have caught this · **FIXED on this branch**

`scripts/secret-scan.sh` reported CLEAN on `main` this morning. It should not
have: two independent, verified defects meant whole classes of committed
credential were invisible to it.

**(i) The history sweep used a narrower pattern list than the working-tree
sweep.** The script defines `CRED_PATTERNS` — eight shapes including Resend,
RevenueCat `sk_`, Stripe `rk_live_`/`sk_test_` — and applied it only to the
working tree. The history sweep carried its *own* hand-written alternation of
five, which did not include Resend.

> **Concrete failure:** a contributor commits a Resend or RevenueCat key in any
> text file, then deletes it in the next commit. The tree scan sees nothing (it
> is gone) and the history scan has no pattern for it. CI reports CLEAN and the
> key is leaked permanently. The tree can be cleaned with a delete; history
> cannot — so the *history* sweep is the one that must be the broader of the two,
> and it was the narrower.

**Fix:** the history alternation is now built from `CRED_PATTERNS` itself, so the
two can never drift again. The one pattern that could have matched its own
definition is both anchored and split, so **no path in the repo is exempt from
either sweep** — see §5(7) for why the earlier exemption was worse than the
problem it solved. Verified: matches a planted `re_xxxxxxxx_…`, matches
`sk_live_…`, does not match `re_short` or ordinary code; exits 0 on `main`.

**(ii) Every check in the file is a text grep, and `git log -p` prints "Binary
files differ" for any document container.** A credential inside one is invisible
to all of them at any pattern strength — which is a whole class this gate could
not see, not a tuning problem.

> **Concrete failure:** a binary document carrying a live credential is
> committed and pushed. Every pattern in the file runs, none can open it, and CI
> reports CLEAN.

**Fix:** a new check fails the scan on document-container and key-material
extensions (`.docx/.xlsx/.pptx/.vsix/.p8/.p12/.pfx/.jks/.keystore/.ovpn/
.mobileprovision` and friends). Filename is the only signal available for a
container the scanner cannot read, so use it. Kept deliberately narrow — no
images, fonts or video — so it stays a rule people trust.

Checked in the index **and** across history reachable from `HEAD`. The index
alone leaves the commit-then-delete case open — a branch that adds the document
in one commit and removes it in the next has a clean tip index, and the history
grep still cannot look inside the blob, so precisely the case where rotation is
the only remedy would pass. `ci.yml` checks out with `fetch-depth: 0`, so the
reachable history is genuinely there to scan. *(This half was added after
review — my first version was index-only and I had justified it with a
shallow-clone concern that does not apply to this job. See §5.)*

**Scoped to `HEAD`, not `--all`, deliberately.** Refs other than the one under
test can carry blobs no PR can purge, and a gate that is red on every build
regardless of the change is a gate everyone learns to click past.
HEAD-reachable is exactly the scope a PR author can act on. `main` and this
branch are both clean, so CI stays green.

Verified in a scratch repository: clean repo exits 0; a repo that commits a
document and deletes it in the next commit is **caught by the history half after
the index half reports nothing**, which is the exact scenario.

### 2b. LOW — three comments assert the opposite of the code they sit on · **FIXED on this branch**

Not cosmetic. Each one describes a security behaviour the code deliberately does
*not* have, so the plausible next edit is a "correction" that reintroduces a
fixed bug. Two were flagged on 20 Aug as informational and were still there.

## 5. Not done, and what review caught in this PR

Review raised **twelve** findings across six rounds — two P1s from Codex, the
rest from the Claude reviewer. **All twelve were real; eleven are fixed here and
one is deliberately declined and filed.** Recorded rather than quietly patched,
because most are defects I introduced while fixing a security gate.

1. **My binary gate was index-only, so it missed commit-then-delete.** I checked
   `git ls-files`, which only sees the tip index, and justified it with "behaves
   identically on a shallow CI clone". `ci.yml` checks out with
   `fetch-depth: 0` — there is no shallow clone on that job, so the rationale was
   wrong and the hole was real: a branch adding a document and deleting it in the
   next commit passed. Verified in a scratch repo that the original version let
   that through. Now scans HEAD-reachable history too. **The irony is the point:
   a gate that only looks at the current tree is the same failure as an audit
   that only looks at the current tree, which is the thing that hid this key for
   a month.**
2. **My pathspec silently narrowed the very sweep this PR set out to widen.** To
   stop the pattern definitions matching themselves I passed `git log` a
   `:(exclude)` pathspec. A pathspec — even a pure exclusion — switches on
   default history simplification, and for a merge TREESAME to one parent git
   then follows *only* that parent. So `git merge -s ours leak-branch` followed
   by GitHub's delete-on-merge, which is a plausible attempt at *tidying up a
   leak*, drops those commits out of the traversal entirely: key still in public
   history, scan prints "history clean". Reproduced: the pre-PR form found the
   planted key, my version found nothing, `--full-history` found it again.
   Fixed with `--full-history`, plus splitting the one literal pattern that
   could self-match so the working-tree sweep no longer needs the exclusion at
   all — this file used to be the single path a credential could hide from
   *both* sweeps.
3. **The binary gate was case-sensitive, so `Secrets.DOCX` walked through.**
   `grep -EI` with a lowercase-only alternation. Uppercase extensions are not
   contrived — they arrive from older Windows tooling and case-insensitive
   volumes. Since filename is by design the *only* signal for a container the
   scanner cannot open, a filename-layer bypass defeats the entire check. Now
   `-Ei`. The `-I` was also dropped: it does nothing useful on a filename list
   and would suppress the whole result set — failing open — on any byte
   sequence grep read as binary.
4. **My own §1a leaked more than it needed to.** It described where the blob
   lives and what kind of file it is, in a report committed to the public repo
   this PR also teaches to enumerate document extensions. That contradicted this
   file's own opening banner. Trimmed to impact and remedy; the locator stays in
   the private notification. *The commit message on this branch's first commit
   still carries the wider phrasing. I have not rewritten it — force-pushing is
   on the irreversible list and, more to the point, redaction is not what closes
   this. Rotation is.*

5. **`grep -aInE` in the history sweep was fail-open, and it predates this PR.**
   `-a` (`--binary-files=text`) and `-I` (`--binary-files=without-match`) set
   the same grep option, so the last one wins — and in `-aInE` that is `-I`.
   Confirmed against this repo's own PNG: `grep -acE` → 1, `grep -aIcE` → 0.
   When the stream looks binary, grep discards **all** of it, `$hist` comes back
   empty, and the script prints "history clean for live-key shapes" — a silent
   pass, byte-identical in the CI log to a real one.

   **I did not take the reviewer's stated trigger at face value, and it was
   wrong.** They said an encoding error (a latin-1 accent, a mojibake commit
   message) would do it; tested in both C and C.UTF-8 locales on GNU grep 3.11,
   a latin-1 byte does **not** trip binary detection. The real trigger is a NUL
   byte, and the reachable path is narrower but genuine: git's own binary
   heuristic sniffs only the **first 8000 bytes** of a blob, so a file that is
   ordinary text for 8kB and carries a NUL after that is classified as text by
   git, inlined in full by `git log -p`, and lands the NUL in grep's input.
   Reproduced end-to-end — with a committed-then-deleted Resend key plus one
   such file, the old form finds **0** and `--binary-files=text` finds **2**.
   On this repo today it is latent (2275 `diff --git` lines under either form),
   but one committed blob from permanent. Now spelled `--binary-files=text` so
   flag order cannot silently decide it.

6. **`core.quotePath` defeated the `$`-anchored extension match.** `git ls-files`
   wraps any path containing a non-ASCII byte in quotes and octal-escapes it, so
   `Château/résumé.docx` comes out as `"Ch\303\242teau/r\303\251sum\303\251.docx"` —
   ending in `"`, not `x`, so the `$`-anchored regex missed it entirely. One
   accented character in a path was a complete bypass of the index half, and it
   is at least as likely by accident (a club with an accented name) as on
   purpose. The pre-existing dotenv check had the same hole. Fixed with
   `-c core.quotePath=false` on all three enumerations. (`rev-list --objects`
   turned out to emit paths raw, so the history half was already safe — passing
   the flag anyway removes the need to know which command quotes.)
7. **The scanner was still the one path where commit-then-delete evaded both
   sweeps** — my earlier "past tense is not yet earned" reply was right to be
   hedged, and review pushed it further. Splitting the literal fixed the working
   tree but the history sweep still excluded this file, so a credential
   committed into the scanner and deleted next commit was invisible to both.
   Fixed properly by **anchoring** the pattern on `"role":"` — the form a real
   decoded service-role JWT payload always has, and which this file's pre-anchor
   commits (carrying the bare literal) never do. Verified: 0 matches in history,
   still matches a real payload. **The pathspec is now gone entirely**, which
   closes the merge-simplification bypass of item 2 by construction rather than
   by a flag someone can later drop.
8. **The extension list omitted the most common carriers.** No `.pdf` — the same
   shape as the incident this check exists for — no archives, no `.kdbx`, and
   `.key` itself was missing so DER-encoded key material passed. Widened after
   checking `git ls-files` on `main` for false positives: zero tracked matches,
   so the gate stays green.
9. **Declined, and filed instead:** the `clientIp()` fallback trusts
   X-Forwarded-For entry [0] on the strength of an ingress it cannot verify —
   it is only reached when `cf-connecting-ip` is *absent*, i.e. exactly when the
   evidence for that ingress is missing. Real point, and the limit is now
   documented in the docstring. **I did not implement the fix:** it is a
   behaviour change to rate limiting on the only unauthenticated endpoint, and
   its failure mode is self-throttling that endpoint entirely if
   `cf-connecting-ip` ever goes missing in production. That is Henry's call with
   eyes on it, not something to fold into a comment-only PR.

10. **My anchor silently narrowed a live-credential pattern.** Anchoring the
    service-role shape on `"role":` (item 7) killed the pathspec, but I wrote
    the anchor demanding *zero* whitespace after the colon — and JSON permits
    it. Every way a human actually produces one of these payloads (jwt.io,
    `jq`, the Supabase dashboard, a pretty-printed log) emits it with a space,
    so the pattern I shipped covered only the **less common** paste shape while
    the bare literal it replaced had covered both. A pretty-printed
    service-role payload committed and deleted would have passed. Fixed with
    `[[:space:]]*`, which also keeps the no-self-match property (in this line's
    own source that token is literal brackets, not whitespace), so the pathspec
    stays gone. Both paste shapes are now regression cases 9 and 10.

    Footnote worth keeping: my first attempt at the fix put a pretty-printed
    example *in the explanatory comment*, and the gate immediately failed the
    build on it. The check works.

11. **Archives were missing from the extension list — a tarball defeats every
    other check in the file.** `.zip/.7z/.rar` were there but not
    `.tar/.tgz/.gz/.bz2/.xz/.zst`, which on a macOS/Linux project are far more
    likely. Verified the full bypass: a `.tgz` holding a `.env.production` with
    a service-role key passes the dotenv rule (path doesn't match), passes both
    binary-name checks (extension absent), and is invisible to both content
    sweeps — `git grep -I` returns 0 and `git log -p` prints only "Binary files
    differ". Zero false positives on this branch, so the gate stays green.
    `.ppk` added too: PuTTY keys start `PuTTY-User-Key-File-2:`, so `PEM_LINE`
    never sees them. Now regression case 11 of 12.

    **This list is open-ended and will never be complete, so further additions
    belong on `BACKLOG.md`, not in another review round.** Two rounds have now
    extended it; the marginal value is falling and the enumeration has no
    natural end. The comment now says to carve out by path rather than removing
    an extension if a build ever legitimately needs one.

12. **Round four raised the disclosure question a third time, and this is where
    I stop.** The specific points were right and are fixed: the scanner comment
    asserted that a *live* credential got past this gate (causal link, now
    generic); the `--all`-vs-`HEAD` rationale mentioned blobs "no PR can fix",
    which paired with a green scan implied a ref scope; and the banner still
    characterised the item's current state. Also corrected a stale paragraph of
    my own in §2a(i), which still described the pathspec that §5(7) removed.

    **But each redaction pass has drawn a reshaped version of the same finding
    — four rounds now — and that is the signal to stop rather than keep going.**
    PR #146 reached this conclusion already and wrote it down: report-side
    redaction has a ceiling, and past that point it is motion, not safety. What
    is left reconstructible is inherent to describing a secret-scanning gate at
    all — the gate cannot work without naming credential shapes and file
    extensions, and this repo will keep publishing security reports.

    **Rotation is what closes this, and nothing on this page substitutes for
    it.** I am not opening further redaction passes on this PR.
