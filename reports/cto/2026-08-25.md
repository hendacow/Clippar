## 2. Security findings

### 2a. HIGH (process) — the CI secret gate could not have caught this, and its two sweeps had drifted apart · **FIXED on this branch**

`scripts/secret-scan.sh` ran clean on `main` this morning while a live Resend key
sat in a pushed blob. Two independent, verified reasons:

**(i) The history sweep used a narrower pattern list than the working-tree
sweep.** The script defines `CRED_PATTERNS` — eight shapes including Resend,
RevenueCat `sk_`, Stripe `rk_live_`/`sk_test_` — and applied it only to the
working tree. The history sweep carried its *own* hand-written alternation of
five, which did not include Resend.

> **Concrete failure:** a contributor commits a Resend or RevenueCat key in any
> text file, then deletes it in the next commit. The tree scan sees nothing (it
> is gone) and the history scan has no pattern for it. CI reports CLEAN and the
> key is leaked permanently. The tree can be cleaned with a delete; history
> cannot — so the *history* sweep is the one that must be the broader of the two,
> and it was the narrower.

**Fix:** the history alternation is now built from `CRED_PATTERNS` itself, so the
two can never drift again, with this file excluded by pathspec so the pattern
definitions don't match themselves. Verified: matches a planted
`re_xxxxxxxx_…`, matches `sk_live_…`, does not match `re_short` or ordinary
code; the scan still exits 0 on `main`.

**(ii) Every check in the file is a text grep, and `git log -p` prints "Binary
files differ" for any document container.** A credential inside one is invisible
to all of them at any pattern strength — which is a whole class this gate could
not see, not a tuning problem.

> **Concrete failure:** a binary document carrying a live credential is
> committed and pushed. Every pattern in the file runs, none can open it, and CI
> reports CLEAN.

**Fix:** a new check fails the scan on document-container and key-material
extensions (`.docx/.xlsx/.pptx/.vsix/.p8/.p12/.pfx/.jks/.keystore/.ovpn/
.mobileprovision` and friends). Filename is the only signal available for a
container the scanner cannot read, so use it. Kept deliberately narrow — no
images, fonts or video — so it stays a rule people trust.

Checked in the index **and** across history reachable from `HEAD`. The index
alone leaves the commit-then-delete case open — a branch that adds the document
in one commit and removes it in the next has a clean tip index, and the history
grep still cannot look inside the blob, so precisely the case where rotation is
the only remedy would pass. `ci.yml` checks out with `fetch-depth: 0`, so the
reachable history is genuinely there to scan. *(This half was added after
review — my first version was index-only and I had justified it with a
shallow-clone concern that does not apply to this job. See §5.)*

**Scoped to `HEAD`, not `--all`, deliberately.** Refs other than the one under
test can carry blobs no PR can purge, and a gate that is red on every build
regardless of the change is a gate everyone learns to click past.
HEAD-reachable is exactly the scope a PR author can act on. `main` and this
branch are both clean, so CI stays green.

Verified in a scratch repository: clean repo exits 0; a repo that commits a
document and deletes it in the next commit is **caught by the history half after
the index half reports nothing**, which is the exact scenario.

### 2b. LOW — three comments assert the opposite of the code they sit on · **FIXED on this branch**

Not cosmetic. Each one describes a security behaviour the code deliberately does
*not* have, so the plausible next edit is a "correction" that reintroduces a
fixed bug. Two were flagged on 20 Aug as informational and were still there.

- `_shared/rateLimit.ts` — `clientIp()`'s **docstring** stated the generic
  X-Forwarded-For rule ("take the LAST entry") as fact. The body does the
  opposite, on measured evidence: Supabase's gateway *overwrites* the header, so
  the last entry is Supabase's own load balancer. Following the docstring would
  restore the bug the body documents fixing — 133 requests from one machine
  fragmented across 14 buckets, and unrelated visitors throttling each other.
- `search-courses/index.ts` and `get-shared-reel/index.ts` — same claim,
  repeated at both call sites. Corrected to match `clientIp()`.
- `lib/supabase.ts` — the header block said the native storage adapter "falls
  back to AsyncStorage silently". **It does not, and must not:** AsyncStorage is
  unencrypted disk and the value is the Supabase session including the long-lived
  refresh token. The real fallback is the in-memory mirror documented 30 lines
  below. A reader who trusted the header and "restored" the fallback would put
  refresh tokens in cleartext on every handset. Rewritten to say so explicitly.

## 3. Correctness review — the 36-hour diff

Two code PRs merged in the window. Both had already been through automated
review and both showed it; I found no new user-visible bug in either, and I am
not padding this section to make it look otherwise.

**#143 — reel scorecard timeline (`reelScorecard.ts`, `editor.tsx`).** Read in
full, including the `holeReelDurationMs` pre-trimmed/`autoTrim*` bounds split and
the `validClips`/`validClipUris` index pairing that replaced the URI
string-matching walk. The pairing is now established where the drop decision is
made, which is the right place, and `inReelClipIds` correctly excludes clips
dropped as unrecoverable. Traced it against native's consumer
(`fastGroupSegments` in `ShotDetectorModule.swift`): hole ranges are contiguous
and cumulative, clip midpoints advance monotonically, so segment order cannot
invert and the `holes.count - 1` fallback is only reachable past the end of the
timeline. Correct.

One thing I checked specifically because it *would* be this bug class:
`getAllClipsInOrder()` prepends `state.intro` and appends `state.outro`, neither
of which belongs to a hole, so a reel with an intro would shift every hole
boundary while the scorecard still started hole 1 at 0. **Not live** —
`setIntro`/`setOutro` have no call sites and both are always null, which
`editor.tsx:549` already records. Worth keeping in mind if an intro card is ever
added: the scorecard timeline would need the offset.

**#136 — performance (`api.ts`, `useEditorState.ts`, home/profile/preview).**
Read in full. The parallelised query pairs have no data dependency between them
and preserve their original semantics; `getRoundStatusCounts` uses the same
`user_id` filter and the same draft predicate as the `getRounds()` call it
replaced, so the Profile tab's two pills cannot drift. `getSignedClipUrls`'
switch to batch `createSignedUrls` keeps the same 7-day expiry and the same
`clips/` prefix strip as the per-clip `getClipUrl` it replaced, and the shots it
signs are pre-filtered for a non-empty `clip_url`, so there is no null path into
it. The prefetch cache is single-use, TTL-bounded, and falls back to a live fetch
on any miss.

**Correction, found while checking the open-PR list below.** I first wrote that
the prefetch cache "is scrubbed on sign-out and account deletion". That is too
generous. It is scrubbed on the *profile sign-out button* and on account
deletion — **not on every sign-out.** `useAuth.ts`'s `SIGNED_OUT` handler calls
`resetLocalAccountState()`, which does `iap.reset()` and nothing else; it never
reaches `clearAccountLinkedCaches()`. A session that ends by remote revoke or
refresh-token failure therefore leaves the departing golfer's round payloads
(GPS + clip storage paths) in memory. Verified against `main` today. This is
PR #145's first finding and it is correct.

**#145 is the one that matters.** It landed on its branch minutes after #136

against `main` rather than taking them:

1. **Scrub misses the non-button sign-out paths** — confirmed above. True.
2. **Retention is process-lifetime** — true. The 15s TTL gates *serving*, not
   *retention*; an entry nobody consumes is only removed on take or clear, so it
   survives until the process dies.
3. **No ownership check on consumption** — true. `takePrefetchedRound` keys on

   `getRound` would enforce. Narrow window (15s, shared handset, mid-navigation
   account switch) but fail-closed to fix, and the fix is the right shape:
   owner-stamp the entry and resolve `null` on mismatch.

**Recommendation: merge #145.** It is a real fix to code that is already
shipping, its verification is green, and leaving it open is how the finding gets
lost — the same way it got lost yesterday. I have not merged it; it is not my PR

### Watch list — not findings, deliberately not fixed

- **`clearReelSourceCache()` in `lib/resolveReelSource.ts`** — session-lifetime
  cache of signed reel URLs, never cleared on sign-out. Same class as the
  prefetch cache #136 fixed, left out of that PR to keep it scoped. Already on
  `BACKLOG.md`; the fix is one line wired into `clearAccountLinkedCaches()`.
- **Export-status handling is inconsistent across the Swift module.**
  `fastExportSegment`, the concat and the mux all require
  `status == .completed`; the two paths that call `cancelExport()` check
  `.failed || .cancelled`; but `trimVideoPassthrough` and `detectAndTrimVideo`
  treat *anything that is not `.failed`* as success and resolve a `trimmedUri`
  for a file that would not exist. **I am reporting this rather than calling it a
  bug: neither of those two sessions is ever cancelled and neither has a
  background-expiry handler, so I could not construct a reachable path to it
  today.** It is a trap for whoever adds background-task protection to the
  auto-trim path — the natural way to do that is `cancelExport()` in the
  expiration handler, and the moment that lands, a backgrounded round import
  starts silently persisting clips that point at files that were never written.
  If that work happens, `guard status == .completed` goes in first.

Neither is touched here. The Swift video-export path is not something to change
on CI-only evidence.

making exactly the mistake this report is about.
