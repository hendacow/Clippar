### The review round found more than the merge did — and it was right

Two automated reviewers went over the branch and raised fifteen things. **Fourteen
were real**, I fixed thirteen, and **most of them were mine** — not pre-existing gaps
in the two old pull requests, but fixes my merge discarded or defects my own patches
introduced. Recording that plainly because it is the most useful thing in this report:
the merge was the easy part, the review is what made the gate correct, and **the way I
did the merge was itself the largest source of new defects in it.**

**My conflict resolution dropped SIX fixes, and that is the lesson of the night.**
I resolved five conflicted files by taking the newer pull request's version wholesale
and hand-porting the one thing I had spotted. Six more fixes lived only in the older
one, and taking a whole file "because it is newer" silently discarded every one. Each
was found by review, none by me. **A dropped fix is invisible in the diff you are
reading** — it looks like nothing at all — which is exactly why merging two competing
rewrites of a security control by picking a side is the wrong method, and I used it.

I only found the last two because I finally stopped asserting I had recovered
everything and went and *compared the two files token by token*. That check took two
minutes and should have been the first thing I did, not the eighth.

The ones I dropped:

**A complete bypass of both filename checks.** Git wraps any path containing an
accented character, a quote or a backslash in quotation marks, so the path ends in
`"` instead of its extension and every extension rule misses it. `key.docx` fails the
gate; `kéy.docx` sails straight through, along with `café/.env`. Reproduced exactly.
It needs no attacker — this is a golf app, and one course or club with an accent in a
committed filename turns both checks off. The older pull request had already found
this, gone *further* than the obvious fix, and left a note in its own report reading
"do not simplify this back out". I simplified it back out.

**The scanner was blind to its own source file.** One pattern contained its own match
text, which forced the scanner to skip its own file in every sweep — making it the one
place in the repository where a committed-then-deleted credential was invisible, and
that is precisely the file someone edits while holding a real key. The older pull
request had closed this too. Worse, when a reviewer first raised it I replied that I
was leaving it deliberately, and defended it. I was wrong and the fix already existed.
Now scoped so every other credential shape scans that file normally; the one residual
is written into the file rather than glossed.

**Two flags on one line of the history sweep.** Without the first, a single tracked
line marking a file "binary" hides a credential from the entire history scan — and
that line can be pushed in the same commit as the key. Without the second, git shows
no changes at all for a merge commit, so **a credential typed into a hand-resolved
merge is invisible**. Measured: 0 matches versus 2, and 0 versus 1. The second is
pointed, because this branch *is* a hand-resolved merge — the operation that dropped
the flag is the one the flag exists to see into.

**A flag that let anyone hide a credential from the content scans** by marking the
file binary — one line, no compression, no exotic filename.

All of them now have regression tests that plant the failure case and fail if the
scanner reports clean — because every test we had only ever proved the scan stays
*green*, which is the half that cannot catch a scanner that has quietly stopped
looking.

### And three of the defects were in the safety guard I had just written

Worth its own heading, because it is the sharpest lesson of the night. Asked to make
the scanner refuse to claim "clean" when it had not actually run, I wrote a guard that
**failed silently in three different ways at once**: the shell option in use reports
the wrong half of the pipeline, the status array does not survive the way I was
capturing it, and the function was running in a subshell so the flag it set was thrown
away. All three have the same shape — *a guard that cannot signal failure is
indistinguishable from a guard reporting success* — which is precisely the bug class
the guard existed to remove. I caught the second only because it made the scan fail on
a clean repository.

**The one I broke outright.** Handing `git log` a pathspec — which the file-exclude I ported
from #147 is — silently switches on history simplification: at a merge that is
identical to one parent for that path, git follows only that parent and **discards
the other parent's history entirely**. So a branch that commits a credential,
deletes it, is merged, and has its ref deleted goes invisible. The reviewer derived
it from the documentation and could not test it, because the copy CI hands the
reviewer is shortened. I could:

| | matches |
|---|---|
| before this PR (no pathspec) | 2 |
| with my pathspec | **0** |
| pathspec + `--full-history` | 2 |

That is the exact false-clean this branch exists to eliminate, reintroduced by the
fix for a different false-clean. Fixed, and the comment now says never to add a
pathspec there without the flag.

**The best of the rest: the service-role key was the least-covered credential we
have.** It bypasses every access rule on every table. Anchoring the decoded-payload
rule was correct on its own terms, but it left detection resting entirely on a rule
that needs the literal variable name — so the same key committed under any other
name matched nothing at all. Now matched by its **encoded** form, which is what
actually authenticates and which carries a fixed fragment whatever holds it.
Measured across every byte alignment: **27/27 service-role keys caught, 0 public
keys caught**, 0 false positives on our own history.

**And the gate was naming files in world-readable build logs.** Three of its checks
printed paths — including, in the sharpest case, the file *and line* of a live
credential. That was survivable while the scan only ran on pull requests. It is not
once the scan runs on **every branch**, which is the change this branch makes: one
push to a branch carrying the exposed document would have written that document's
exact path into a log anyone can read for ninety days, and deleting the branch
afterwards does not delete the log. All three now report counts only.

Also fixed: the archive list covered `.tgz` but not plain `.tar`, which is the
cheapest way of all to hide a file from a text scan; and a count that was computed
after truncating its own input, so any incident with more than five hits reported
exactly "5".

**Two I declined**, both stated on the pull request with reasons:

- A fail-closed switch on the share-link rate limiter. It is the right shape, but
  it is a behaviour change to a live limiter on our only unauthenticated page,
  where the safe-looking version throttles every visitor at once. That is the
  standing open decision, not mine to settle. I did take the half that is
  clear-cut — see below.
- Exempting `reports/` and all documentation from credential scanning to remove
  prose false positives. That would carve the hole exactly where this project has
  demonstrably put sensitive detail before.

**One correctness fix came out of it**, in code this branch did not otherwise
touch: the share-link rate limiter passed a caller-supplied header straight into
the database as a primary key, unvalidated and unbounded. An anonymous visitor
could write one row per value they invented, of any length.

**And my first fix for that was itself too weak** — the fourth of my own defects
the review caught. I checked the value looked address-ish rather than checking it
*was* an address, so `1.2.3.4`, `01.2.3.4` and `001.2.3.4` each got their own
allowance: one visitor could spell themselves into as many allowances as they
liked, without forging anything. The limit is now computed from a single canonical
form of the address, so every spelling of one visitor collapses onto one allowance.
Real visitors are unaffected — verified against every existing case.

### 🟢 The application's own security posture — clean, re-derived from source

- **Row Level Security.** Re-resolved the create/drop chain across 001 → 019 in
  order. No table where one signed-in user can reach another's rows. The storage
  policies all join through round ownership and cover both the per-clip and the
  reel key shapes. The one open question a migration left for a live check — a
  bucket whose key is predictable from a user id — was answered on 23 Aug: that
  bucket does not exist.
- **Edge functions.** All 11 verify the caller: eight against the auth server, the
  two payment webhooks by signature or configured secret, and the one public
  endpoint by design. **None trusts a client-supplied user id.** The public one
  derives the object it signs from the round record rather than from any value a
  visitor can influence, which is what stops it being a signing oracle.
- **Client.** Session tokens in the encrypted store, not plain device storage. No
  interpolation into database filter strings.
- **Working tree.** No credential of any live shape.
