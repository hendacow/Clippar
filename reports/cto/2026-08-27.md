## Part 1 — Correctness

### 1.1 The reel and its scorecard are timed by two different clocks — CONFIRMED

Status: **mechanism confirmed in code from both sides. Magnitude still
unmeasured.** Raised 2026-08-26 as "mechanism present, unproven"; I re-derived it
independently tonight before reading that write-up, and it holds.

The app trims each clip with `AVAssetExportSession` under
`AVAssetExportPresetPassthrough` (`ShotDetectorModule.trimVideoPassthrough`).
Passthrough copies samples rather than re-encoding, so it cannot cut mid-GOP and
the file it produces is **at least** as long as the window that was asked for.

Neither trim entry point ever measures what came back:

- `trimVideoPassthrough` resolves `trimmedUri` and nothing else
  (`ShotDetectorModule.swift:281-283`).
- The automatic path records the *requested* width
  (`lib/reelScorecard.ts:115-117`).
- The manual re-trim path does the same — `durationMs: trimEnd - finalStart`
  (`app/round/preview.tsx:772`).

Native, composing the reel, reads the **real** file: `fastParseClips` clamps to
`asset.duration`, and for a pre-trimmed clip that value *is* the clip's whole
length. So the scorecard's hole boundaries are laid out on requested time while
the video plays on actual time, and the error accumulates clip by clip.

**New detail, and it explains the shape of the symptom.** `fastGroupSegments`
assigns each clip to a hole by matching its midpoint against the scorecard's hole
ranges, and defaults to `sc.holes.count - 1` when nothing matches
(`ShotDetectorModule.swift:2319`). Once accumulated drift pushes a clip's midpoint
past the final hole's `endMs`, *every remaining clip* falls into that default. The
failure is therefore not a gentle smear that grows — it is correct, correct,
correct, then the last hole's card sitting over all of the rest.

**Not fixed, deliberately.** Every repair runs through video export, which this
routine does not modify on its own judgement, and the fix cannot be validated
anywhere but a real device.

**What would settle it:** one export on a phone, comparing the requested trim
width against the produced file's duration. If they match, this finding closes.
If they do not, the gap is the per-clip drift and the fix is to measure the file
and record that instead.

### 1.2 Swing detection and hole arithmetic — no findings

I read the swing state machine (`scanGate`, `selectEpisode`, `resultFromEpisode`)
looking for the failure modes that would cost a user a clip: non-terminating
scans, index arithmetic that can run off the end, episodes selected from the
wrong window. The scan advances monotonically on both branches, the compacted
index is mapped back correctly, and the gate conditions are internally
consistent with Vision's coordinate convention.

Hole ordering (`orderedHoleNumbers`, `((startHole - 1 + i) % 18) + 1`) is correct
for both start holes at both round lengths, including the 18-hole wrap from a
tenth-tee start.

One judgement call worth recording rather than reporting as a bug: `scanGate`
substitutes a fixed shoulder height of `0.55` when the shoulder joints are not
detected in a frame (`ShotDetectorModule.swift:3554`), and the full-swing gate
then compares the backswing peak against that fabricated value. On footage where
the shoulders drop out this makes the gate's decision partly synthetic. Whether
that ever changes an outcome is a tuning question answerable only on real
footage, so I am not calling it a defect.

### 2.2 🟠 NEW — the Python pipeline service has fall-open defaults and an unscoped endpoint

The legacy Flask processing service at the root of this repository has two
distinct problems:

**(a) Several configuration values fall back to constants published in this
repository.** If the deployment sets them, this is inert. If any is unset, the
control it is supposed to provide is worth nothing, because the fallback is
readable by anyone.

**(b) One mobile endpoint authorises the caller but never checks that the
resource belongs to them.** It hands back a long-lived download link for a stored
object named directly from the request. The token gating it is shared across every
installation of the app rather than per-user.

**These two compose, and that is the part that matters.** If the relevant value
in (a) is unset on the deployment, the gate in front of (b) is already public,
and what remains between a stranger and a stored reel is knowing its identifier.

**What bounds it, stated honestly, because a later reader should not
over-correct.** That identifier is a random UUID and cannot be guessed or
enumerated. A review argued it is effectively public because the identifier
travels inside the media URL handed to anyone who opens a public share link. I
checked, and that part is true — but the conclusion does not follow: someone
holding a share link can already watch that reel, so the endpoint gives them
nothing they did not have. The exposure is therefore **real but not
self-serving**: it needs an identifier obtained some other way — a log, a
screenshot, a support thread, a URL pasted somewhere.

So this is "fix it because ownership checks are not optional", not "reels are
leaking today". I would rather write that down than leave the next reader to
infer a severity nobody measured.

**The route, the token-recovery method, the specific configuration values and the
rest of the severity reasoning are in the private notification, not here.**

**How this differs from what is already on file.** The 2026-08-20 security audit
recorded the bundled token as a *spend* risk — someone burning Clippar's compute
on the job-submission endpoints — and left it as a described, unfixed Medium. The
read path is a different and worse class: it is other customers' finished reels,
not the bill. The fall-open defaults are not in that audit or any other report in
this repository.

**Severity is deployment-dependent and I could not resolve it.** I tried to check
whether the service answers. My network path cannot reach that hosting provider
at all — a known-good control host there also failed — so the result is
inconclusive, not negative. DNS resolving proves nothing either way, because the
provider answers for its whole wildcard domain regardless of whether a service
exists behind a given name. **Treat this as unknown, not as safe.**

**Not fixed, deliberately.** Making these fail closed is a change to
authentication, which this routine does not make unattended, and it carries a
real cost in the direction nobody would want: if the service *is* live without
those variables set, a fail-closed change takes it down. That is a decision with
facts attached that only Henry has.

**Recommended, in order:** (i) establish whether the service is deployed at all;
(ii) if it is not, delete it or archive it out of this repository — it is dead
code carrying live risk; (iii) if it is, set all three variables, treat the
mobile token as already public, and scope the reel endpoint to the caller.

### 2.3 🟢 Row Level Security — re-verified from the migrations, clean

Traced from the migration files rather than the schema, and from scratch rather
than from yesterday's conclusion.

Every one of the sixteen tables has RLS enabled. Ownership policies scope to
`auth.uid()`. The `rounds` policy that originally had no `TO` clause — and so was
readable by `anon` — was dropped in `013`. Storage policies for the `clips`
bucket all join through `public.rounds` on `r.user_id = auth.uid()`, covering both
the per-round keyspace and the reel keyspace, and the bucket is forced private.
`apple_credentials` has RLS on and no policy at all, which is correct: it is
service-role-only by design.

**I found no table where user A can read or write user B's rows.**

The standing caveat still applies and is worth repeating: this is the *migrations*,
not the deployed database. A checkout cannot tell you what is applied.

### 2.4 🟢 Edge functions — every entry point verified

All twelve. Every user-facing function derives the caller's identity from
`supabase.auth.getUser(token)` and uses that id — none trusts a user id supplied
in the request body. The functions that run as service role and skip the JWT are
the two provider webhooks (authenticated by their own signature or configured
header), the internal course-sync job (bearer key), and the public share
endpoint.

`get-shared-reel` deserves a specific note because it is the only unauthenticated
entry point and it holds up well: it derives the storage key from the round's own
id rather than from the client-writable `reel_url` column, which is what closes
the signing-oracle hole; it returns a uniform "not available" so it cannot be used
to probe which share tokens exist; and it rate-limits before parsing anything.

The remaining bundled value is the pipeline token covered in 2.2.

## Reporting

This is the third consecutive night spent partly on keeping unfixed security
detail out of a public report. The underlying problem is structural, not a
wording problem: **nightly engineering reports are published to a public
repository while they enumerate holes that are not yet closed.**

Recommendation, unchanged and now with a third data point behind it: move these
reports to a private repository and leave a plain changelog here.

**And the "eventually" in that argument arrived in this very report.** The first
version of 2.1 and 2.2 named the credential provider, the exact vulnerable route,
and the method for recovering the token in front of it — while both findings are
unfixed and one has an unresolved deployment state. A review caught it and was
right. I had drawn the line correctly for the file path in 2.1 and wrongly for
everything beside it, which is precisely the failure mode of a convention that
depends on judgement: it does not fail loudly, it fails in the half you were not
thinking about.

Worse, one of those was already settled. On 26 August three reviewers asked for
the provider's name to be removed from a public report; that session refused
twice and then conceded it was wrong. **I reintroduced it tonight.** A decision
that has to be re-won every night is not a decision, and that is the strongest
argument for the structural fix rather than a better habit.

The redactions are applied. What was already pushed cannot be unpublished, which
is the usual shape of this: rotation and merging are the remedies, tidying is
not.

## Android

Priority 2, not started, estimate unchanged: **4–6 months solo for parity, 3–4 if
the ball-flight tracer is cut from v1.**

Reading the compose path closely tonight adds one argument, and it is for cutting
the tracer. The reel pipeline leans on two Apple-only pieces with no Android
counterpart — `AVVideoCompositionCoreAnimationTool` for the burned-in scorecard,
and `VNDetectTrajectoriesRequest` for the tracer — and the fast path is built
around a *third* Apple-specific property: that `AVAssetExportPresetPassthrough`
can concatenate format-uniform segments without re-encoding. That is what makes a
100-shot round compose in tens of seconds instead of eight minutes. Android has no
drop-in equivalent, so an Android reel is not a port of this code; it is a second
implementation of the same idea with different performance characteristics.

The sharper point is verification, not effort. Both of tonight's correctness
observations sit in the video pipeline, and neither can be settled without a
physical device. On iOS that is at least a solved problem — there is a working
version to compare against. On Android there would be nothing to check a new
implementation against and no reference output. **Rebuilding the least verifiable
part of the product first, with no oracle, is the risk the Android number should
be read against.**
