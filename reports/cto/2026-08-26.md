### 🟠 MEDIUM (correctness) — the reel and its scorecard run on two independent clocks

**New this run. Mechanism confirmed by reading; magnitude NOT measured. Not patched.**

This is a third route into the same failure the 08-23 and 08-24 HIGHs described — the
scorecard sitting over the wrong shots — and the 08-24 fix does not close it. That fix
was a large improvement and I am not retracting it; this is the residual it left.

**The chain.** For an auto-trimmed clip:

1. `composeClips` (`app/round/editor.tsx:1242`) sends native `trimStartMs: 0,
   trimEndMs: -1` — "play the whole trim file".
2. Native honours that literally: `fastParseClips` (`ShotDetectorModule.swift:2269`)
   resolves `effectiveEndMs = assetDurationMs`, **the real file's duration on disk**.
3. JS has no access to that number. `holeReelDurationMs` contributes
   `autoTrimEndMs - autoTrimStartMs` — the **requested** window width. SQLite agrees
   with JS, not with the file: `markClipTrimmed` writes
   `duration_seconds = (autoTrimEndMs - autoTrimStartMs)/1000`.
4. Those JS widths become the hole boundaries in `buildReelScorecard`, and native
   matches each clip's midpoint against them using a cursor accumulated from the **real**
   durations (`fastGroupSegments:2316-2326`).

**Why the two numbers need not agree.** The trim is written by `AVAssetExportSession`
under `AVAssetExportPresetPassthrough` (`trimVideoPassthrough:240`). Passthrough copies
samples instead of re-encoding, so it cannot cut mid-GOP. And **neither trim entry point
ever returns the output's real duration** — `trimVideoPassthrough` resolves only
`{trimmedUri}` (`:281`), and `detectAndTrimVideo` resolves `trimmedUri` plus the
*requested* bounds (`:495`). Nothing in the app measures the file it just wrote.

**Concrete failure, if the durations do diverge.** A golfer plays 9 holes, 18 clips, each
auto-trimmed to a requested 3s. If passthrough snapped each output to ~3.5s, native's
cursor is 9s ahead of the scorecard's clock by the end. Clip midpoints land in later
holes' ranges, so **the card shows a hole ahead of the shot on screen**, and once the
cursor passes the last hole's `endMs` every remaining shot falls to
`holeIdx = sc.holes.count - 1` (`:2319`) and **the final hole's card sits over the rest
of the reel**. The export reports success.

**Both compose paths, and the fast path is unconditional.** `composeReelOnDevice:2748`
always tries `composeReelFast` first; legacy is an error fallback only. Legacy has the
same mismatch even more directly — its CALayer fades are driven straight off
`hole.startMs / 1000.0` (`:2911`) over a composition built from real durations.

**What I could NOT establish, and it is the whole question.** Whether AVFoundation's
passthrough trim writes an edit list that makes the output's reported `duration` equal
the requested range. If it does, the two clocks agree and this never fires. If it does
not, it fires on every export. **I cannot resolve that by reading, and I did not guess.**

**The measurement that settles it** — one round on a device, from the existing logs:
`[Clippar.Trim] OK passthrough` gives the requested window per clip; compare against the
real duration of each `trim_*.mp4` in the caches directory. Equal → close this finding.
Different → it is a HIGH and the fix is to stop sharing a clock at all (send native the
hole boundaries as **clip indices** rather than milliseconds, which removes the
assumption instead of tuning it).

**Not patched, deliberately.** Every candidate fix changes either the native trim
contract or the video-export ordering. Standing rule holds; both need a device.

I did correct the comment in `lib/reelScorecard.ts` that asserted the width "is the
file's length exactly". It is an estimate, and the code now says so.

## Security posture — clean, nothing new

Checked independently against the migrations and function sources, not read off prior
reports.

- **Secrets in the working tree.** Clean. Every hit from the credential-pattern sweep is
  the scanner's own pattern list (`scripts/secret-scan.sh`), a test fixture, a doc, or a
  `.example` placeholder. No service-role JWT anywhere: I decoded every `eyJ…` in the
  tree and none carries `role: service_role`. Every edge function reads its key from
  `Deno.env`.
- **Secrets in history.** One finding, and it is the CRITICAL above. Exactly three
  office/credential-extension blobs have ever been committed: the document in question,
  its Word lock file, and a financial-model spreadsheet. I extracted and
  credential-pattern-scanned the spreadsheet's full contents this run — no key, token,
  JWT or account-number pattern in it. (Scanned, not read line by line.)
- **RLS.** Re-resolved the whole `CREATE`/`DROP POLICY` chain across all 18 applied
  migrations in order. **No table where user A can reach user B's rows.** The permissive
  early policies are all genuinely dropped: `courses`/`holes` global UPDATE (007) by 013,
  public `rounds` SELECT (001) by 013, bucket-wide `clips` storage (008/011) by 017 and
  019. `apple_credentials`, `sync_course_usage` and `api_rate_limit` have RLS on and no
  policy at all — service-role only, which is correct and deliberate.
- **The `rounds` UPDATE column grant, checked rather than assumed.** 013 revokes the
  blanket grant and re-grants a column list that includes `id` and `user_id`, which looks
  alarming. It is not exploitable: the policy is `FOR ALL … WITH CHECK (auth.uid() =
  user_id)`, so a row whose new `user_id` is not yours is rejected, and `id` is a unique
  primary key so it cannot be retargeted onto a round that exists. 015's additive
  `GRANT UPDATE (start_hole)` still stands — 019 does not revoke `rounds` again — so the
  tee-off-on-10 feature keeps its write.
- **Storage.** All three `clips` policies (SELECT/UPDATE/DELETE) join through
  `public.rounds` on `r.user_id = auth.uid()` and cover both `<round_id>/…` and
  `reels/<round_id>.mp4`. UPDATE checks the destination key too, so a rename cannot land
  in someone else's keyspace.
- **Edge functions.** All 11 entry points verify the caller. Eight via
  `supabase.auth.getUser(token)` — verified against the auth server, not decoded locally.
  `stripe-webhook` via `constructEvent`, `revenuecat-webhook` via a configured shared
  secret. `get-shared-reel` and `search-courses` are unauthenticated by design, both rate
  limited. **None trusts a client-supplied user id.** `sync-courses` additionally gates
  its privileged actions on `admin_users` and caps everyone with a per-user daily counter
  in a service-role-only table.
- **Client.** Auth tokens in `expo-secure-store`, not `AsyncStorage`. No interpolation
  into `.ilike()` / `.or()` filters.

## PR #145 — I checked its three claims against `main`, and all three are true

Recommending it again, because leaving it open is how a real finding gets lost twice.

1. `clearRoundPrefetch()` is called from exactly two places on `main`, both in
   `lib/localWipe.ts` (`:114`, `:146`). It is **not** called from
   `useAuth.ts`'s `resetLocalAccountState()`, which is what runs on `SIGNED_OUT`. So a
   session ending by itself — password changed elsewhere, refresh token expired — leaves
   the previous golfer's round payloads in memory.
2. `clearRoundPrefetch()` on `main` is a bare `cache.clear()` with no expiry timers, so an
   untaken entry is retained for the process lifetime. The TTL gates *serving*, not
   *retention* — the payload stays reachable in the heap.
3. `takePrefetchedRound()` is keyed on round id alone and returns `hit.promise` with no
   owner check, so a cache hit is served without ever re-running RLS.

Narrow to exploit — it needs a shared handset and a badly-timed account switch — but the
fix is small, tested, and already written.
