## Findings by severity

### HIGH (correctness) — wrapped rounds scored the front nine at par 4 — FIXED

`buildHoleDataFromPars` (`lib/scorecardLogic.ts`) mapped par slot *i* to hole
`startHole + i` with no wrap. #135 made the play sequence wrap after 18, and the
scorecard entry screen labels slot *i* with the wrapping `liveHoleNumbers[i]` — so in an
18-hole round from the 10th tee, the par the golfer entered for "Hole 1" was stored
against hole **19**. `getParForHole` never finds holes 19–27, so all nine wrapped holes
silently scored `DEFAULT_PAR = 4`, that wrong par was persisted into `scores.par` /
`total_par`, and burned into the exported reel's scorecard. The coverage gate
(`presetCoversRound`) compares wrapped hole-number *sets*, so it waved the broken preset
straight through — the exact failure the gate exists to prevent.

**Fix:** map with the same `((startHole - 1 + i) % 18) + 1` formula as
`liveHoleNumbers`, plus a lockstep test pinning the two functions together for every
round shape. Identical behaviour for all previously-possible rounds.

### MEDIUM (correctness) — Prev Hole button dead for half a wrapped round — FIXED

`app/(tabs)/record.tsx` disabled Previous Hole with `currentHole <= startHole`. In an
18-from-10 round, holes 1–9 are numerically below the start, so the button was disabled
for nine real holes even though the hook's positional `previousHoleTarget` steps back
correctly (1 → 18 across the wrap). The disable now asks `previousHoleTarget` itself, so
button state and behaviour cannot disagree.

### MEDIUM (security) — GolfCourseAPI key in git history — NEEDS VERIFICATION

`EXPO_PUBLIC_GOLF_COURSE_API_KEY=JL2H…` was committed as a literal in
`clippar_app/.env.development.local.example` (commits `4f82b9f`, `21b0463`). It is
scrubbed from the working tree but remains in history, so it is compromised until
rotated. The 2026-07-29 audit's DEPLOYED section says a new key was already set on dev +
prod — **Henry should confirm at the GolfCourseAPI.com dashboard that the old `JL2H…`
key is disabled.** Impact if live: it is a 50/day free-tier quota key — a DoS key, not a
data-access key. Per policy, no history rewrite attempted.

### LOW (security) — pipeline key still ships in the client bundle

`EXPO_PUBLIC_PIPELINE_API_KEY` (`constants/config.ts:19`) is still read by `lib/r2.ts`
and `lib/pipeline.ts` and is inlined into the bundle when `EXPO_PUBLIC_PIPELINE_URL` is
set. This is the legacy pipeline path, superseded by the Modal dispatch in
`process-round`. Either confirm the URL is unset in production builds or retire the
path. Not fixed here — deciding the legacy path's fate is a product call.

## Security posture — clean

- **Secrets:** no service_role JWT, no `sk_live`, no Stripe secret, no SMTP password, no
  AWS key, no private-key PEM in the working tree or full history. The anon JWTs in
  `clippar-web/public/r.html` are publishable by design.
- **RLS:** every table in migrations 001–019 has RLS enabled and owner-scoped
  reads/writes (`auth.uid()` directly or via `rounds`-ownership joins). No `USING
  (true)` on user data, no missing `WITH CHECK`. The column-level GRANTs (013/015/017/019)
  correctly fence billing and dispatch columns.
- **Edge functions:** all 11 verify the JWT or carry an explicit control
  (signature check, shared secret, IP rate limit). None trust a client-supplied user id.
  `stripe-webhook`'s error-echo leak from the 2026-07-29 audit is fixed.
- **Client:** auth tokens live in expo-secure-store (Keychain), not AsyncStorage.
  `.ilike()`/`.or()` filters are parameterized or interpolate server-generated values
  only. No injection.
- **Prior audits:** all four P0–P2 tenant-isolation findings (2026-07-31) verified
  closed in-tree by migration 019. 2026-07-29 items spot-checked fixed.
