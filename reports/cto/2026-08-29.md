## Part 1 — Correctness

### 🟢 `canonicalIp()` — exercised, not re-read. Does what its docblock claims.

This function decides the rate limiter's keyspace, so a spelling it fails to
collapse is a multiplied cap on the one endpoint with no JWT. I ran it against
~50 inputs covering every claim in its own docblock, plus junk and edges.

Confirmed:

- **Every spelling of one IPv4 host collapses to one subject.** `1.2.3.4`,
  `01.2.3.4`, `1.2.3.4:8080`, `1.2.3.4%eth0`, `[1.2.3.4]:80`, `::ffff:1.2.3.4`,
  `0:0:0:0:0:ffff:1.2.3.4`, `::ffff:102:304` and `[::ffff:1.2.3.4]:443` all
  return `1.2.3.4`. The v4-mapped fold is the one most likely to have been
  missed and it holds through all four spellings.
- **Every spelling of one IPv6 host collapses to one /48.** Case, leading zeros,
  `::` placement, brackets, port and zone index — including `[…%eth0]:443`,
  the ordering case a previous round got wrong — all return
  `2001:db8:1:0:0:0:0:0`.
- **Distinct prefixes do not collide.** `2001:db8:1::`, `2001:db8:2::` and
  `2001:db9:1::` stay three subjects.
- **Idempotent.** `canonicalIp(canonicalIp(x)) === canonicalIp(x)` on every
  value that parses — worth checking because the output is fed back as a
  database key.
- Junk fails closed to the shared bucket: `dead`, `....`, `0`, `1.2.3`,
  `256.1.1.1`, `1::2::3`, `2001:db8:::1`, 60 characters of `x`.

**No finding.** Recording it because "we reviewed it six times" is not the same
evidence as "we ran it", and this is the first time it has been run.

The non-routable collapse the docblock accepts is real and behaves as described:
`::`, `::1`, `::1.2.3.4` and `::ffff:0:1.2.3.4` all land on one subject. None of
those arrives as a client source address through Cloudflare, so it costs nothing
here.

### 🟡 LOW — a taken prefetch entry stays reachable in the heap until its timer fires

`lib/roundPrefetch.ts`. `takePrefetchedRound` removes the entry from the `Map`
but does not cancel that entry's expiry timer, and the timer's closure captures
`entry` — so the round payload (GPS + clip storage paths) stays reachable for up
to `TTL_MS + 500` (15.5s) after it has been consumed.

Bounded and **not** an account-crossing leak: every way a session ends calls
`clearRoundPrefetch()`, which cancels all timers, and the ownership gate blocks a
cross-account take regardless. This is the same class of remanence the PR set out
to close, one path short of complete. Not worth a change on its own; filed to
`BACKLOG.md`.

**On the export-status item, I can now say why it has never fired**, rather than
just "nothing calls cancel". The three sites that check only `.failed` —
`trimVideoPassthrough` (:264), `detectAndTrimVideo` (:460) and
`stitchClipsOnDevice` (:1743) — are also the three paths that **do not request a
UIKit background task**. `cancelExport()` is only ever called from a background

`ShotTracer` (:972) register one — both of which correctly check
`.failed || .cancelled`. When the user backgrounds the app mid-trim, iOS
interrupts the export as `AVErrorOperationInterrupted (-11847)`, which arrives as
`.failed` and **is** caught.

So the gap is genuinely unreachable today, and it becomes reachable the moment
anyone gives trim or stitch a background task — which is a plausible next
optimisation. Left unpatched for the fourth run, deliberately: it is in the
video-export path, there is no live trigger, and no device here to verify on.

### 🟢 Row Level Security

Sixteen tables have RLS enabled across migrations 001 → 019. The one policy that
ever allowed cross-tenant reads — `"Shared rounds are publicly viewable"` on
`rounds`, which let the anon key bulk-harvest every published round's
`share_token` and `reel_url` — was dropped in 013 and **has not been

would expose every user's raw clips. Intact.

I re-derived the create/drop chain at statement level this run rather than
re-reading a previous report's conclusion, but I did not re-run the per-table
reasoning against a live database — there is none reachable from here.

### 🟢 Edge functions — with a correction to how we have been counting them

**None derives identity from a client-supplied user id.** `process-round` in
particular re-checks `round.user_id !== user.id` after the lookup, and
`sync-courses` rejects an anon-key-only call outright rather than treating the
gateway's `verify_jwt` as proof of a user. That is the finding, and it holds.

But the count this report has been repeating is wrong, and a reviewer on the
pull request was right to say so. The line has been *"eight verify against the
auth server, two webhooks, and the one public endpoint by design"*. Re-derived
from source, it is:

- **Seven** mandatorily resolve a real end user and reject the request
  otherwise: `apple-link`, `create-payment-intent`, `create-share-link`,
  `delete-account`, `process-round`, `redeem-code`, `sync-courses`.
- **Two** are webhooks authenticated by signature or configured secret:
  `stripe-webhook`, `revenuecat-webhook`.
- **Two** — not one — are reachable **without a signed-in user**:
  `get-shared-reel` and `search-courses`.

`search-courses` calls `auth.getUser(token)` only *if* a token happens to be
present, and only to upgrade the rate-limit subject from an IP to a user id. A
signed-out caller is expected and served: the onboarding funnel is pre-signup.

The two public endpoints are **not** public in the same way, and the difference
is worth keeping straight rather than flattening as I flattened it:
`get-shared-reel` runs with no gateway JWT check at all, while `search-courses`
deploys normally and the gateway's `verify_jwt` is satisfied by the project anon
key — which ships in the app bundle, so in practice anyone can call it.

**Why it matters, beyond tidiness:** `search-courses` is the endpoint that
**spends money upstream** (the paid GolfCourseAPI budget, 250 units a day). It
is therefore the second endpoint whose only real defence is the rate limiter,
which is the same limiter the IPv6 note below is about — a connection this
report drew nowhere because it had `search-courses` filed under "verified".
Its own code already knows this: it validates the request body *before*
consuming the upstream budget, precisely because malformed traffic used to be a
cheaper denial of service than the exposed key it replaced.

Nothing is exposed by the miscount and nothing changes in the code. Recording it
because the same sentence appears in the 20 Aug and 28 Aug reports and would
have kept propagating.

### 🟢 Share links — inert by flag, not by accident

`is_published` is read in four places and **written nowhere**, which would mean
every share link ever minted returns "not available". This is deliberate and
documented: `constants/config.ts` sets `reelLinksEnabled: false` (Henry's call,
2026-08-04 — a share link is a reel we pay to hold forever for a free user), and
the comment there and in migration 019 both warn against "fixing" it by
restoring the dropped RLS policy. Verified, not a finding, recorded so a future
run does not re-discover it as a bug.

### 🟠 Two older security items, both still open, both decisions

Neither is new and neither moved this run. Naming them so "clean scan" is not
read as "clean slate":

- **The legacy Flask service at the repo root (`app.py`)** — fallback
  credentials and an unlocked admin page. Confirmed present on `main` again

- **`sync-courses` matches admin privilege by email address** as well as by user

### 🟡 Watch, do not change — IPv6 rate limiting is now per /48

`get-shared-reel` is capped at 120/hour per subject, and every IPv6 caller is now
keyed on its /48 rather than its address. That is the correct trade against an
attacker who owns a whole prefix, and the docblock argues it carefully. The cost
it accepts is real though: mobile carriers can put many subscribers behind one
/48, so a reel that circulates inside one carrier's network can 429 genuine
visitors. It is parity with IPv4 carrier-grade NAT, so it is not new exposure —
but it is the first thing to look at if share links ever start failing under
load. **No change made.** Sharing is off by flag anyway, so this cannot bite
before that flag flips.

## The routine's own environment is broken — and this is the fourth night

**Not a new finding. It was filed to `company-brain/BACKLOG.md` on 26 Aug**, by
this seat, having been caught two nights running, with the remedy written on the
row: *"Put `git fetch --unshallow` in the routine's own standing instruction so
it cannot start blind. CTO's own fix, not Henry's."* Nobody applied it, so it
caught the next run too, and it caught me tonight. I checked the backlog after
writing this section up as a discovery, which is its own small lesson about
reading the file before claiming a find.

**The nightly checkout is a shallow clone.** In that state
`scripts/secret-scan.sh` correctly refuses to report clean — it cannot see a
credential that was committed and then deleted — and exits 1. The verify suite
has a test that runs the scanner, so:

```
npm run verify   →  546 tests, 545 pass, 1 fail
```

before a single line is changed. The failing test is
`the secret scanner is green on the current tree`, and its own failure message
says plainly `this checkout has no history, so this is not a finding`.

Both halves of that are working as designed. The problem is what it does to
**this routine**, whose standing instruction is "run `npm run verify` before
opening the PR; if it fails, fix it or drop the change — never open a red PR":

- a run that reads the red test as a defect burns the night chasing nothing;
- a run that reads it as noise learns to discount a red verify, which is worse;
- and **the security half of the audit silently does not happen** — the history
  sweep, which is the sweep that matters for a deleted-but-published credential,
  cannot run at all.

That third one is the real cost, and it is why a backlog row was the wrong place
for this: a row that sits unactioned costs a *fifth* of the audit every night it
sits, silently. Tonight's clean history result only exists because I ran
`git fetch --unshallow` first, and nothing told me to.

**Applied tonight, where the backlog row said it belonged:** the CTO role file in
`company-brain` now says to unshallow before verifying, so the next run reads it
as part of the role rather than having to think of it. No code change here — the
scanner and the test are both right, and making either quieter would be trading a
real signal for a green tick.

## Android

**Unchanged at the top line: 4–6 months solo for parity, 3–4 if the ball-flight
tracer is cut.** I am not going to re-quote the breakdown to look busy; it is in
`reports/cto/2026-08-23.md`.

One correction to our own standing estimate, because it has been repeated four
times and half of it is out of date. The CTO role file says two pieces have *no
Android equivalent at all*: `VNDetectTrajectoriesRequest` and
`AVVideoCompositionCoreAnimationTool`.

**The first is still true. The second is not.** `androidx.media3`'s `Transformer`
now gives you the two things the reel path actually needs — `OverlayEffect` /
`BitmapOverlay` for burning the scorecard card into the frames, and
`Composition` + `EditedMediaItemSequence` for concatenating segments, including
transmux-without-re-encode when the inputs are format-uniform. That is a genuine
structural analogue to `fastExportSegment` → `fastPassthroughConcat` →
`fastMixMusic`, which is ~600 lines of the Swift module. It is not free — the
card is a `CALayer` tree built in Swift and would have to be rebuilt as
Android drawing — but it is a port, not an invention.

So the Android cost is concentrated harder than we have been saying: **it is the
detector, not the exporter.** The swing state machine's thresholds are tuned to
Vision's coordinate and confidence conventions and have to be re-tuned on real
Android footage, and the tracer has no counterpart at all. Cutting the tracer
from v1 remains the single decision that moves the number, and it is already off
behind a flag, so cutting it costs nothing today.

Stated honestly: this is a correction from knowing the Android media stack, not
from having built it. It is worth a one-day spike before anyone commits a date to
it — but it is a better starting position than "no equivalent at all".
