# Code review — 2026-08-20

**Mode:** No commits in the last 36 hours (last change Aug 10), so per the rotation (day 20 → days 11–20) this is a deep review of the **React Native app code**. Coverage: the capture path (`record.tsx`, `useCamera`, `useShutter`, `useRound`, `storage.ts`, `media.ts`, `useLocation`), the editor (`useEditorState`, `editor.tsx`, `PreviewPlayer`, `ClipTrimModal`), import (`import.tsx`), the backup pipeline (`uploadQueue.ts`, `r2.ts`, `subscription.ts`, `iap.ts`), and the home/profile tabs. This is the first run of this routine, so nothing was previously cleared.

**Headline:** the capture path itself is in excellent shape — but the **cloud backup pipeline has three independent bugs that each silently lose a clip from the cloud while telling the user their round is backed up** (findings 1–3), and the editor's "Delete clip" button doesn't actually delete anything (finding 6). Since "your footage survives reinstall" is a core promise, findings 1–5 are the ones I'd fix before launch.

---

## Findings

### A. Cloud backup silently loses clips

**1. A clip that exhausts its retry budget is dropped forever, and the round is reported as backed up** — `lib/uploadQueue.ts:201-204` + `:131-135`. `uploadRoundClips` `continue`s past any clip with `upload_retry_count >= 6`. If the skipped clip was the only failure, the loop returns cleanly, so the caller marks the queue row `done`, emits `backup:complete`, and deletes the row. The clip stays `uploaded = 0` with an `upload_error` — but `getClipsWithUploadErrors` (`lib/storage.ts:1398`) has **zero callers**, so the error never reaches any UI, and `profile/rounds.tsx` buckets the round as synced because the queue row is gone. On reinstall that clip is gone. *Fix:* if any clip was skipped, leave the row in `error` (or a terminal `partial`) and don't emit `backup:complete`. **Confidence: high** (traced and verified).

**2. A backup interrupted by an app kill never resumes** — `lib/uploadQueue.ts:129` sets the row to `in_progress`; `getQueuedRoundUploads` (`lib/storage.ts:1481-1483`) selects only `('pending','error')`, and nothing anywhere resets stale `in_progress` rows. iOS suspending the app mid-upload (routine for a multi-clip round on cellular) strands the round: every future launch skips it, "Retry backup" can't see it, and the rounds screen shows "Backing up…" forever. The file's own header ("progress survives app kill") is currently untrue. *Fix:* at the top of `processUploadQueue`, reset `in_progress` rows to `pending` (safe — the module is single-flight). **Confidence: high.**

**3. Clips enqueued during an in-flight pass are destroyed by the unconditional dequeue** — `lib/uploadQueue.ts:118/:161` (snapshots) vs `:135` (`removeQueuedRoundUpload`). `processUploadQueue` is single-flight: an `enqueueClipUpload` that lands while a pass is running re-creates the queue row as `pending` and then no-ops (the in-flight promise is returned). When the running pass finishes the same round from its stale snapshot, it unconditionally deletes the queue row — including the fresh `pending` state. `useCamera` fires `enqueueClipUpload` after **every** saved clip, so stop-shot-record-next-shot while clip N uploads is the normal cadence. Self-heals only when a *later* enqueue arrives for the same round — which the round's final clip never gets. *Fix:* re-run `getUnuploadedClips` before marking `done` and loop until it's empty. (A conditional delete alone is NOT enough: `markQueuedRoundStatus('done')` runs first and would overwrite the concurrent `pending` back to `done`, leaving a row `getQueuedRoundUploads` never selects — the completion transition itself must be conditioned, e.g. `UPDATE … SET status='done' WHERE round_id=? AND status='in_progress'` plus a matching conditional delete, with the loop fix still preferred.) **Confidence: high.**

**4. Clips over 50MB can never upload, and the error message describes compression that never ran** — `lib/r2.ts:65`, `:94`, `:119-124` vs `lib/uploadQueue.ts:211`. The queue is the only production caller of `uploadClipToStorage` and always passes `skipCompression = true`, which gates **both** compression passes — so for the real upload path they are dead code, and any >50MB file throws `"Clip is NMB after two compression passes"` when zero passes ran. Over-50MB files are routine: confidently-classified putts keep the full recording (up to 120s of 1080p ≈ 150MB per `useCamera`'s own comment), and imports enqueue before the editor's deferred trim runs. Combined with finding 1, the clip then gets silently dropped after 6 identical failures. *Fix:* let the >`MAX_FILE_SIZE` re-compress pass run even when `skipCompression` is set (the flag is about preserving quality, not about accepting an unuploadable file). **Confidence: high** on the dead branch; the >50MB frequency depends on putt/import mix.

**5. A RevenueCat outage caches "not subscribed" and silently turns backup off** — `lib/iap.ts:382-391` vs `lib/subscription.ts:83-88`. `checkSubscriptionDeterminate` relies on `iap.isProActive()` **throwing** to mark the store indeterminate — but `RevenueCatProvider.isProActive` wraps everything in `catch { return false }` and the stub returns `false`, so `storeIndeterminate` is unreachable and every indeterminate branch below it is dead. A StoreKit-only subscriber whose `getCustomerInfo()` fails (RC outage, receipt refresh failure) while the `profiles` query succeeds with `'free'` (normal, since the RC→profile webhook isn't wired) gets a **determinate false** that `getProStatus` then writes into the user-scoped cache — the exact false negative the cache design promises can't happen. Pro features lock and `uploadQueue` returns early with no event. *Fix:* add a determinate variant of `isProActive` that rethrows store errors. **Confidence: high** that the code is dead; real-world frequency medium.

### B. Editor data integrity

**6. "Delete clip" deletes nothing** — `hooks/useEditorState.ts:330-338`. `removeClip` only filters React state: no `deleteLocalClip`, no file unlink, no `markReelStale`. The editor's long-press → "Delete clip" → confirm (`editor.tsx:1981`) removes the card, and the next reload (focus effect at `editor.tsx:571-580`) resurrects it from SQLite — while `handleClose` tells the user "Your edits are saved as a draft." Because the reel isn't marked stale, an already-composed reel silently keeps the clip. (Two independent reviews converged on this one.) Also: the clip card's X (`editor.tsx:267-281`) fires the same `removeClip` with **no confirmation at all**, unlike the menu path. *Fix:* mirror `moveClipToHole` — persist via `deleteLocalClip`, unlink the returned `fileUris`, `markReelStale`; add a confirm to the card X. **Confidence: high** (verified the call path and the reload).

**7. The auto-trim batch reverts concurrent user edits — an excluded clip lands in the exported reel** — `hooks/useEditorState.ts:932` (and `:681`). `updateClipInState(clip.id, () => updatedClip)` ignores the updater's current-state argument and writes back an object built from the pre-batch snapshot (`{ ...clip, ... }`). Any edit made while the batch runs (tens of seconds on a 20-clip import) — exclude, move-to-hole, manual trim — is reverted in memory when that clip's trim completes. SQLite keeps the user's edit, so `getAllClipsInOrder()` (state-driven) exports the clip the user excluded, and a reload later "fixes" it — the hardest kind of bug to report. Every other updater in the file uses the correct `(c) => ({ ...c, ... })` form; these two are the anomaly. *Fix:* merge a delta: `updateClipInState(clip.id, (c) => ({ ...c, ...trimFields }))`. **Confidence: high** (verified `updateClipInState`'s signature and both call sites).

**8. Every imported round shows up as an "Unfinished round" with a Resume/Discard trap** — `app/round/import.tsx:626-634`. `saveLocalRound` writes with the schema default `status = 'in_progress'` and import never sets the local round to `finished` (line 803's `'ready'` is the remote row). `getOrphanedRounds` selects exactly `status = 'in_progress'`, so after any import the Record tab shows "Unfinished round at ⟨course⟩": **Resume** drops the user onto the live camera recording into the imported round (shot numbers colliding), and **Discard** deletes the round they just imported. It also shadows any genuinely unfinished live round. *Fix:* after a successful import, `updateLocalRound(roundId, { status: 'finished', finished_at: … })`. **Confidence: high** (verified: no status write exists on the import path).

**9. Quick-import scores survive the Front 9/Back 9 toggle and corrupt totals** — `app/round/import.tsx:352`, `787-789`, toggles at `1554-1609`. The toggle rebuilds `pars` but never clears `scores`, and both totals reduce over `Object.values(scores)` rather than the round's current holes. Score holes 1–9 then tap "Back 9": the next screen still claims "45 total strokes", `handleBulkImport` reads `scores[10..18]` → all 0 → **every selected video is silently discarded** and the flow dead-ends; re-entering scores instead persists ~+54 `score_to_par`. *Fix:* total over `getOrderedHoleNumbers()` and clear `scores`/`selectedScoreCell` in the toggle handlers. **Confidence: high** (verified the reduce and the toggle handler).

### C. Library player trim paths (each can destroy a highlight)

**10. The library trim panel opens on the full original, discarding the detected swing window** — `components/editor/PreviewPlayer.tsx:199-219`. For auto-trimmed clips, `ScoreCollection` deliberately passes `trimStartMs = 0` / `trimEndMs = -1` and carries the real window in `autoTrimStartMs/autoTrimEndMs` — which `SimpleTrimPanel` never reads (declared at lines 59-60, zero uses). The probe effect sets the handles to `0 .. full original duration`, so a user who opens scissors on a 5s highlight sees a ~30s timeline, and saving replaces the highlight with the untrimmed clip. `ClipTrimModal` gets this right via `getInitialTrimBounds`; the two panels diverged. *Fix:* use `getInitialTrimBounds(clip, dur)` in the probe effect and initial state. **Confidence: high.**

**11. The `-1` "whole file" sentinel escapes into raw arithmetic and the native trim call** — `PreviewPlayer.tsx:314-319` emits `finalEnd = -1` whenever the user drags only the start handle (the normal "cut the boring lead-in" gesture); the sole consumer `ScoreCollection.tsx:643-671` passes it straight into `trimVideo(source, startMs, -1)` — the Swift side builds `CMTimeRangeFromTimeToTime(start, end: -0.001s)`, a negative range — and computes `newDurationMs = -1 - startMs` (negative), persisted to `duration_seconds` if the export somehow resolves. When the export rejects, the `catch` only `console.warn`s and the trim offsets written to the row are no-ops for pre-trimmed clips — so the user's edit has no effect anywhere and no error shows. `ClipTrimModal:241` and `preview.tsx:769` both translate the sentinel correctly; this is the one call site that doesn't. *Fix:* resolve the sentinel against the clip duration before `trimVideo` and the subtraction. **Confidence: high** (verified both ends and both correct siblings).

**11b. Trims saved from a hole card never mark the reel stale** — `ScoreCollection.tsx:678-682` walks `playerRoundGroups` to call `markReelStale`, but `handlePlayHole` (`:622`) always sets it `undefined` and single-round Play All (`:600`) does too — exactly the primary paths. A trim saved there updates the row but the round page never shows "Re-compose reel", so the composed reel silently keeps the old cut. Also `:671`: the `updateClipEditorState` await has no catch and `onTrimSave` is invoked un-awaited, so a SQLite failure is an unhandled rejection and the player state update never runs. *Fix:* carry `roundId` on `PreviewClip` (available at build time) and stale from that; catch the persist. **Confidence: high** (verified the `undefined` assignments).

**12. A failed re-trim closes the modal as if it succeeded and the edit vanishes** — `ClipTrimModal.tsx:247-252`. On `trimVideo` rejection it logs and calls `onSave` with no `sourceOverride`; for a pre-trimmed clip every consumer discards raw offsets against a trim file, so nothing changes anywhere — but the modal closed, the reel was marked stale, and the user believes they trimmed. *Fix:* `Alert` and keep the modal open. **Confidence: high.**

**13. `probeDuration` fabricates 5000ms on failure and can cut a clip to its first 5 seconds** — `ClipTrimModal.tsx:85-119`. If the original file can't be loaded (evicted cache is treated as routine elsewhere), the modal proceeds with a real 30s video on a claimed 5s timeline; dragging the end handle to the far right then saving takes the `finalEnd → durationMs = 5000` branch and permanently trims to the first 5 seconds. *Fix:* return `null` on probe failure and fall back to the source timeline instead of inventing a duration. **Confidence: medium** (mechanism verified; requires the original to load in the export but not the probe, or the probe to fail transiently).

**14. Multi-round player timers: unkillable transition/error timers** — `PreviewPlayer.tsx:723-748` re-arms the round-transition `setTimeout` from a 50ms poll without clearing the previous one (`advance` lacks the `showTransition` guard its siblings have), so a stack of timers keeps re-setting `currentIndex` for 1.5s and survives unmount; the 300ms error auto-advance timer (`:536`) is likewise never cleared, and its stale closure can dismiss the player after the user tapped back. *Fix:* guard `advance` on `showTransition`, clear before re-arming, and clear the error timer in the effect cleanup. **Confidence: high** on the code shape; exact tick counts depend on player timing.

### C2. Editor screen (compose/share paths)

**14b. Compose finishing after the user left the editor force-navigates them** — `editor.tsx:1332-1339` + `:2024-2027`. The export sheet's backdrop dismiss has no `composing` guard, so mid-compose the user can dismiss, leave the editor, and go elsewhere; when the native `composeReel` resolves (up to a minute later), an uncleared 800ms `setTimeout` fires `router.replace('/round/<id>?exported=1')` and yanks them out of whatever screen they're on. *Fix:* mounted-ref guard around the navigation, clear the timer on unmount, block backdrop dismiss while composing. **Confidence: medium-high.**

**14c. Reel scorecard timeline desyncs from the composed video when clips are dropped** — `editor.tsx:1151-1175` builds the scorecard windows from all non-excluded clips, but `composeClips` (`:1235-1266`) contains only the URIs that survived recovery — any dropped or URI-less clip shifts every later hole's card window, so the reel shows the wrong hole/score from that point on. The code already counts `totalMissing` but only writes a transient progress string. Related: the Supabase-fallback load path has `durationMs: 0` on every clip, collapsing all windows to `0..0`. *Fix:* derive scorecard and composeClips from the same list; alert when clips were dropped. **Confidence: medium-high.**

**14d. Compose clip↔URI realignment can match the wrong clip by filename suffix** — `editor.tsx:1243-1253`: the resync loop's `uri.includes(`${clip.id}.mp4`)` matches recovered file `.../15.mp4` against clip id `5`, composing clip 15's file with clip 5's trim bounds. Rare (needs a dropped clip followed by a recovered one with a suffix-colliding id) but the fix is to use the recovery pass's existing index→URI map instead of string matching. **Confidence: medium** on the path, low on frequency (verified the `includes` is real).

**14e. Silent failures the user reads as success** — three small ones, same theme: per-hole **Share** (`editor.tsx:735-758` → `clipShare.ts:139-147`) returns silently on stitch failure — spinner, then nothing (the multi-hole path alerts correctly); a music track that fails to resolve (`editor.tsx:1189-1196`) composes the reel **without music** with only a console.warn, discarding the `hasMusic` flag that comes back; and `ScoreCollection`'s category/date fetch (`:555-589`) has no stale-response guard, so switching Pars→Bogeys quickly can leave par holes listed under the Bogeys tab. *Fixes:* return/check a boolean and alert; confirm before composing without music; `cancelled` flag in the effect. **Confidence: medium-high / medium.**

**14f. A clip still queued for auto-trim is tappable; a manual trim saved there gets overwritten** — `editor.tsx:142-151`: the "Waiting…" spinner is a sibling view, not a hit-test blocker, so the user can open the trim modal on an untrimmed clip and save — moments later `processOneClip` overwrites their values with the detected window. *Fix:* `if (clip.needsTrim) return;` in the card's `onPress`, matching the screen-level gates. **Confidence: medium.**

### D. Smaller items

**15. Reel-upload temp files leak** — `lib/r2.ts:320-343`, `:370-377`: when the second compression pass runs, the first-pass 720p temp is never deleted (only the last `uploadUri` is), and cleanup isn't in a `finally`, so any upload failure leaks every temp — per retry. Same shape in `uploadClipToStorage` (less reachable — the queue skips compression). *Fix:* collect temp URIs and delete in `finally`. **Confidence: high** for the two-pass orphan.

**16. `handleImport` re-entrancy + related import nits** — `import.tsx:589-612`: `await supabase.auth.getUser()` (network) runs before `setImporting(true)` with no synchronous guard — a double-tap creates two rounds, and because `persistAsset` *moves* picker files, the second round's rows point at deleted files. Also: the persisted filename hard-codes `.mp4` (`:667`) where every other call site uses `videoExtension()` — a renamed `.mov` can fail export; `persistAsset` never throws, so the documented catch-fallback is dead and a failed persist silently stores the purgeable cache path (compare the returned uri instead); a mid-import SQLite failure leaves an orphaned remote round with no rollback. *Fix:* `importingRef` flipped synchronously; `videoExtension(clip.uri)`; compare `persistAsset`'s return; best-effort round cleanup on the catch. **Confidence: medium-high.**

**17. Recorded `duration_seconds` includes the 5–10s MP4 finalize** — `hooks/useCamera.ts:443` computes duration when `recordAsync` *resolves*, which is after the native finalize (the file's own comments put that at 5–10s), plus ~200ms of start overhead. Auto-trimmed swings get corrected by `markClipTrimmed`, but putts and no-detection clips keep the overstated value, and `ClipTrimModal`'s non-probed branch uses it as the timeline length — so a putt's trim timeline is too long by the finalize time (dead zone at the end, mis-scaled handles). *Fix:* snapshot `Date.now()` in `stopRecording` (or read the asset's real duration) instead of timing the promise. **Confidence: high** on the mechanism (per the code's own documented finalize model); impact is modest.

**18. Home-screen thumbnail cache never hits for reel-less rounds and grows unbounded** — `app/(tabs)/index.tsx:85`, `:259-278`: the cache is keyed by the preview URI, but reel-less rounds get a freshly-signed URL (new token) on every fetch, so every Home focus/refresh regenerates up to 5 native thumbnails and adds permanent Map entries. *Fix:* key by round id. **Confidence: medium.**

**19. Dead code worth deleting** —
- `hooks/useEditorState.ts`: `trimClip` (~175 lines, zero callers — and it carries the *pre-fix* putt ordering that would point React state at a just-deleted file if ever wired up), `reorderClips`, `updateClipDuration` (both unused).
- `lib/api.ts:1148-1169`: `getSignedReelUrl` — zero callers, and signs against a `reels` bucket that doesn't exist (reels live at `clips/reels/…`).
- `app/round/import.tsx`: the `setSanityWarning` block (`:174`, `:2193-2223`) is unreachable — the ">8 clips on a hole" warning UI exists but nothing ever sets it; unused `detectSwing` import and `HOLE_GAP_MS` constants.
- `lib/uploadQueue.ts` + `lib/storage.ts`: `attempt_count` is maintained and never read, so permanently-failing rounds (deleted remotely, legacy `local_` ids) retry on every launch and connectivity change forever — cap it in `getQueuedRoundUploads`.
- `app/(tabs)/index.tsx:312-327`: cold mount runs `fetchRounds()` twice (focus effect + mount effect).
