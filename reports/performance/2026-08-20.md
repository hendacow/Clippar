# Performance — 2026-08-20

First run of the daily perf pass. Focus: perceived latency on the two things
that matter — screen-to-screen load time, and warming the next screen's data
before the user asks for it. Baseline `npm run verify` was green before and
after (typecheck clean, 512/512 tests).

The app's reel-export and detection code (Swift) is already disciplined about
passthrough vs re-encode on most paths; the JS data layer had several genuine
request waterfalls on the busiest screens. This pass collapses those and adds a
prefetch on the single most-travelled navigation edge.

---

## 1. The single biggest perceived-latency win available right now

**On-device reel export re-encodes the whole reel even when it doesn't have to.**
Native, **not implemented here** — it touches the video-export path and must be
applied and watched on a device (Henry).

`ShotDetectorModule.swift` `composeReelFast` / `fastExportSegment` (~L2359–2439)
**always** attaches an `AVMutableVideoComposition` and exports every segment at
`AVAssetExportPreset1920x1080`, even when there is no scorecard overlay and no
music — i.e. `overlay == nil`. In that state the composition only applies a fill
transform that, for clips all shot on the same camera (the normal case), reduces
to identity: **the re-encode changes no pixels.**

The sibling function `stitchClipsOnDevice` (L1649–1692) already does this right —
it tests `uniformFormat` (all clips share `naturalSize` + `transform`), sets the
track's `preferredTransform`, exports **Passthrough**, and restores identity +
falls through to a re-encode on any failure. `composeReelFast` never got the same
treatment.

- **What the user waits for:** tapping "Create reel" / export in the editor or
  preview screen. The file's own comment estimates ~8 min for a 100-shot round on
  the legacy path; the segment split with 3-way parallelism already cuts that to
  roughly a third.
- **What the change saves:** for the uniform + no-overlay + no-music case, it
  removes the encode *entirely* — a ~12-clip / ~48s reel goes from a 1080p H.264
  encode with a CoreAnimation composite (tens of seconds, scales with length) to a
  container-level sample copy (~1–3s, roughly constant). Order **10–30×**, and it
  is the case most reels fall into.
- **Why it's not in this PR:** correctness is hardware-dependent. Mixed-codec
  sources in one composition can make a passthrough export fail (the `-11838`
  family the code already documents), so the uniformity gate **and** the
  export-failure restore/re-encode fallback both have to be present and verified
  on a real export. This is exactly the class of change the brief says to leave
  for a device. Recommended as native change #1.

Full native analysis (10 findings, ranked, with line numbers) is in
[§4](#4-native-pipeline-findings-analysis-only-not-implemented).

## 2. Prefetch map

The navigation graph from `expo-router`, and what should be warmed on each edge.
This is the artefact to grow over successive days — today establishes the two
highest-traffic edges and the trigger discipline. Legend for **when**: `render`
(as the source list paints), `scroll` (row enters viewport), `press-in` (finger
down, before release), `press` (on tap, overlaps the nav transition).

| Edge | Trigger | Warm | Status |
|---|---|---|---|
| **Home list → `round/[id]`** | **press** (overlaps slide-from-bottom ~300ms) | `getRound(id)` (rounds + shots) | **Implemented** (`lib/roundPrefetch.ts`) |
| **Home hero → `round/[id]`** | press (same) | `getRound(id)` | **Implemented** |
| Home list → `round/[id]` | scroll-into-view (first ~5 rows) | first thumbnail via `expo-image` `prefetch`; poster frame | Recommended — see §3 |
| `round/[id]` → `round/editor` | render of detail (editor is the primary CTA) | `useEditorState` clips already loaded on detail; warm signed clip URLs | Recommended — evaluate |
| `round/[id]` reel → playback | render of `ReelStage` when `status === READY` | `expo-video` source + poster; the reel URL is already resolved in `computeRoundStatus` | Recommended — evaluate |
| Record → `round/preview` | on capture-complete | preview already receives the just-recorded URI in-process | OK today (no fetch) |
| Library → reel playback (compilation) | press on "Play all" | `getHighlightCompilationClips` signs URLs on tap | Recommended — warm on tile-active |

**Cost honesty.** Prefetch is only free when the trigger tracks real intent. Both
rows and hero warm on **`press`** (a committed tap), not `press-in` — `press-in`
fires the instant a finger lands even when the gesture becomes a scroll, so on a
long library it would warm `getRound` for every row the user merely scrolls past
(flagged in review; corrected before merge). `press` warms exactly one payload,
only when a round is actually opened, and still overlaps the ~300ms
slide-from-bottom transition, so the win is kept without the waste. Warming *every*
row on render would have the same scroll-waste problem; thumbnail prefetch (§3)
should likewise be capped to the first few visible rows.

## 3. Changes made

All are safe waterfall collapses (independent `await`s that had no data
dependency on each other) plus one additive prefetch. Each keeps identical
observable behaviour and output ordering.

### 3.1 Round detail opens a round trip sooner — `hooks/useEditorState.ts` `loadFromLocal`
- **Before:** `getLocalRound` → `getLocalScores` → `getClipsForRound` → remote
  `holes` fetch, four fully sequential awaits. The remote holes fetch (the slow
  one) waited behind two local SQLite reads.
- **After:** `getLocalRound` first (the others need its `course_id`), then the two
  local reads and the remote `holes` fetch run in one `Promise.all`.
- **Saves:** one remote round trip on **every native round-detail open** — this is
  the #1 navigation target, so it's the highest-traffic of the collapses.
- **Correctness:** `courseHolePars` is only consumed by `buildHoleSections` at the
  end; nothing between the reads used the holes result. No ordering change.

### 3.2 Editor / web round-detail load — `hooks/useEditorState.ts` `loadFromSupabase`
- **Before:** remote `scores` fetch then remote `holes` fetch, sequential.
- **After:** both in one `Promise.all` (independent — both keyed off the
  already-fetched round).
- **Saves:** one remote round trip on editor open (and web round-detail).
- **Correctness:** unchanged — both feed `buildHoleSections`; clip URL signing
  (already parallel) is untouched.

### 3.3 Home load — `app/(tabs)/index.tsx` `fetchRounds`
- **Before:** remote `scores` query (for the Birdies+ best-hole) → then the local
  SQLite `clips_count` backfill, sequential.
- **After:** the remote scores query and the local clips backfill run concurrently;
  both complete before `computeRoundStatuses` (which reads `clips_count`).
- **Saves:** overlaps a ~100–300ms remote round trip with the on-device reads on
  every Home focus.
- **Correctness (checked carefully):** the `clips_count` backfill mutates the
  `mapped` objects in place; the `best_hole` remap then spreads those same objects,
  so it must — and does — run after both promises resolve. `computeRoundStatuses`
  still runs strictly after `clips_count` is final, so status derivation is
  unchanged. This ordering is load-bearing and is commented in the code.

### 3.4 Prefetch the round-detail payload on the Home → detail edge — NEW `lib/roundPrefetch.ts`
- **Before:** `round/[id]` only started `getRound` (rounds + shots) once it had
  mounted — a guaranteed spinner on every tap.
- **After:** a small single-use, 15s-TTL cache. Home fires `prefetchRound(id)` on
  the committed tap (`onPress` for rows and the hero); `round/[id]`'s `fetchRound`
  consumes the warmed payload if present. `getRound` runs during the
  slide-from-bottom transition, so the payload is usually in hand by the time the
  screen mounts.
- **Saves:** turns the tap's cold-fetch spinner into an instant (or near-instant)
  paint on the app's busiest edge.
- **Correctness / why it's safe:**
  - It's the *identical* query the detail screen already runs.
  - Single-use (consumed on read) and TTL-bounded, so it only ever affects the
    very first paint — `round/[id]` still refetches fresh on focus, so the
    freshness contract is unchanged.
  - A warmed entry that errored resolves to `null` and the consumer falls straight
    back to a **live** `getRound(id)` — it never trades correctness for speed.
  - Scrubbed on session end: `clearRoundPrefetch()` is wired into
    `clearAccountLinkedCaches()` (every sign-out) and `wipeLocalUserData()`
    (account deletion), so the warmed payload (GPS + clip URLs) never survives into
    a next account on a shared handset — the spec-5.5 discipline the app applies to
    its other account-linked caches.
  - Triggered on `press` (committed tap), not `press-in`, so scrolling the list
    never warms rounds the user doesn't open.

**Verification:** `npm run typecheck` clean; `npm test` 512/512. UI behaviour on
device (the actual spinner-vs-instant feel, and the SQLite/remote fallbacks) is
Tier-3 and wants a device confirm, but the logic is a pure query-warming layer
with a live fallback, so the risk is contained to first-paint timing, not data.

## Changes recommended but deliberately NOT made

- **All native pipeline findings (§4).** The brief is explicit: leave the Swift
  concurrency model and export ordering alone unless certain, because those bugs
  are subtle, hardware-dependent, and invisible to CI. Documented below with line
  numbers and reasoning for Henry to apply on a device.
- **Thumbnail / poster `expo-image` prefetch** on scroll-into-view (prefetch map
  row 3). Higher value than it looks but needs the cap-to-visible-rows discipline
  and a device to confirm it doesn't cause jank or waste data; deferring until the
  edge is measured.
- **Round detail's duplicate round fetch.** `round/[id]` calls `getRound` (rounds +
  shots) *and* `useEditorState` independently loads the same round. On native the
  editor path uses local SQLite first so there's no duplicate *remote* call, but
  the two could share one payload. It's a refactor with real surface area (two
  different shapes, two consumers) — noted, not done, low urgency.

## 4. Native pipeline findings (analysis only, NOT implemented)

Full read of `clippar_app/modules/shot-detector/ios/ShotDetectorModule.swift`
(4343 lines). None of these are implemented — they are for Henry to apply and
watch on a device. Ranked by payoff.

1. **Passthrough fast path for `composeReelFast`** (L2359–2439) — the §1 win.
   Uniform + no-overlay + no-music → passthrough concat, mirroring
   `stitchClipsOnDevice` L1649–1692. **10–30× on reel export.** Must keep the
   uniformity gate and the export-failure re-encode fallback.

2. **Double full-clip Vision pass on non-baseline strategies.**
   `detectAndTrimVideo` L316 runs `extractPoseFrames` over the whole clip, then for
   any `strategy != "baseline"` the variant (`velocityPeak`/`audioFused`/
   `aboveShoulderGate`) calls `extractPoseFramesOriented` — a *second* full decode +
   Vision pass — and the first result is then used only for a `count >= 5` guard.
   Hoist the strategy check above L316 and extract once. **~50% of detection wall
   time** on every non-baseline clip. Low effort.

3. **GCD thread explosion in the segment fan-out.** `composeReelFast` L2628–2662
   dispatches *all* N segment blocks onto the global concurrent queue immediately,
   each then parking on the concurrency semaphore *inside* the block (L2632). AV
   concurrency is correctly capped, but an 18-hole round enqueues 18 blocks that
   overcommit GCD's pool. Acquire the gate before dispatch, or use an
   `OperationQueue` with `maxConcurrentOperationCount`. Low effort.

4. **Main-thread hygiene in the compose path (three small ones).**
   - `DispatchQueue.main.sync` for `beginBackgroundTask` (L2737, L3069) stalls the
     compose worker on user tap and is a latent deadlock shape — start the bg task
     on main *before* the fan-out, or use `main.async`.
   - `UIScreen.main.scale` read off the main thread (L2346 via L2638; L2896) —
     capture once on main and pass down.
   - `sendEvent` (bridge hop) called while holding the serial state lock
     (L2647–2656) — mutate counters in the lock, emit outside it.

5. **Frame-read decimation happens after color-convert; per-frame handler.**
   `extractPoseFrames` (L696–705) applies the `frameStep` stride *after* the sample
   buffer is produced, so AVFoundation scales + BGRA-converts all 5-of-6 frames it
   then discards. Push decimation below the output stage
   (`AVAssetReaderVideoCompositionOutput` with `frameDuration`, or
   `generateCGImagesAsynchronously(forTimes:)`). Also, a fresh `VNImageRequestHandler`
   per frame — swap for `VNSequenceRequestHandler`. Constant-factor win on every
   frame of every clip. Medium effort.

6. **Low-risk overlaps.** `detectAudioTransients` is called sequentially right
   after pose extraction despite a comment claiming it runs "in parallel"
   (L316–317, L527–530) — genuinely independent, use `async let`/`DispatchGroup`.
   `sceneGreenSignal` decodes 3 sample frames serially (L1141–1163) — batch via
   `generateCGImagesAsynchronously`. Parallel `AVURLAsset` property loads
   (`loadValuesAsynchronously`) *before* the serial composition-insert loop
   (`fastParseClips` L2250–2294 opens 100 assets serially for a 100-clip round).

7. **Adaptive concurrency is sampled once; no thermal signal.**
   `composeReelFast` reads `os_proc_available_memory()` once (L2619–2621) and holds
   that worker count for the whole compose; `thermalState` appears nowhere in the
   module. Re-sample per segment and observe
   `.thermalStateDidChangeNotification`. Mostly moot once #1 lands (passthrough
   does no encoding).

8. **Bounded Vision pool inside `extractPoseFrames`** (L696–748) — decode and
   Vision are serialized though the results are independent. Real N-way potential,
   but interacts with the JS-side 1–3 clip pool (`useEditorState.ts` L1079) and the
   deliberate `alwaysCopiesSampleData = false` retention trap (L681). High effort,
   do last.

**Correctly serial — do not "optimize":** the composition insert loops
(`stitchClipsOnDevice` L1572–1637, `composeReelOnDevice` L2789–2872,
`fastPassthroughConcat` L2449–2467, music loop L2510–2519) all carry a running
`insertTime` cursor into a non-thread-safe `AVMutableComposition` and must stay
serial. Only the asset *property loads* inside them are parallelizable (finding 6).

## 5. Second pass (same day): further waterfalls collapsed

A follow-up sweep the same day over the screens the first pass didn't reach
(profile, preview, subscription, paywall, storage layer). All changes below are
on this branch; `npm run verify` green (typecheck + 512/512).

### Changes made

- **`getSignedClipUrls`: one request instead of one per clip** (`lib/api.ts`).
  The old comment said "Supabase doesn't have batch sign" — storage-js has had
  `createSignedUrls` (single POST for a list of paths) for years. The editor's
  Supabase load path (`useEditorState.loadFromSupabase`) now uses it too, so a
  cloud-loaded round signs all its clips in **1** round trip instead of N
  parallel HTTPS requests (N = shots in the round; the repo's own measurement
  puts each storage call at 600–800 ms on production). Same 7-day expiry,
  same key-by-original-path contract, failed paths still skipped silently.
- **`useSubscription.refresh`: 4 serial round trips → 2 parallel**
  (`hooks/useSubscription.ts`). It awaited `getProStatus()` (StoreKit +
  profile), then a full Auth-server `supabase.auth.getUser()`, then re-fetched
  the same profile row. Now: local `getSession()` for the user id, and the
  entitlement + status reads run together. This chain gates visible UI — the
  Cloud-backup switch renders off+disabled until it clears, and the "Go Pro"
  card flashes for subscribers — and re-runs on **every app-foreground**.
- **Preview no longer loads twice on mount / blanks on return**
  (`app/round/preview.tsx`, `hooks/useEditorState.ts`). Its focus effect fired
  `editor.reload()` on first focus, concurrently with `useEditorState`'s own
  mount load — the whole waterfall (round + scores + clip signing) ran twice.
  First focus is now skipped. And `loadRound` only surfaces `loading` when
  nothing is rendered yet, so a re-focus revalidates behind content instead of
  swapping the screen for a full-screen spinner (the fetch still runs and
  replaces state wholesale — freshness unchanged).
- **Home no longer double-fetches on mount** (`app/(tabs)/index.tsx`). The
  mount `useEffect` fired `fetchRounds()` alongside `useFocusEffect`'s
  identical mount run — two full chains (queries, status I/O, thumbnails)
  racing on first paint. The focus effect owns the initial fetch; the
  post-upload-queue refetch stays (it can genuinely change data).
- **Profile tab counts: full-table download → `id,status`**
  (`app/(tabs)/profile.tsx`, new `getRoundStatusCounts`). The tab re-fetched
  every column of every round on each focus to render two pill numbers.
- **`getUserStats`: shots-count ∥ scores** — both keyed on the same
  `roundIds`, were serial. (Currently has no call sites; freebie.)

### Recommended, deliberately not made (JS)

- **ScoreCollection: 18 queries → 3.** `fetchCounts` calls
  `getScoreHighlights` once per category — 5 calls × (rounds + scores + shots)
  fetching near-identical data — then a 6th trio for the selected category.
  One rounds + one scores fetch computes all five counts locally. ~1.5–3 s.
  Biggest remaining JS win; wants its own focused PR.
- **SQLite migration gate.** First DB touch runs ~35 serial `ALTER TABLE`s
  (~30 of which throw and are caught) on every launch — a
  `PRAGMA user_version` gate saves ~100–300 ms off whichever screen touches
  storage first. Touches every user's DB init → own carefully-tested PR.
- **Import thumbnail fan-out.** Bulk import spawns an uncapped
  `getThumbnailAsync` per clip (~90 concurrent `AVAssetImageGenerator`s on a
  big import) — the same OOM-kill shape `preview.tsx`'s filmstrip already
  fixed with a settle timer. Crash-prevention more than latency.

### Native addendum (ShotTracer.swift — flag OFF in prod, for when it ships)

The §4 analysis covers `ShotDetectorModule.swift`; the tracer path
(`ShotTracer.swift` + `useEditorState.processAllTracers`) has three compounding
costs for when `config.tracer.enabled` flips: the JS batch is fully serial
(~5 s/clip × ~12 traceable shots ≈ 60 s; the sibling trim batch's 1–3-wide
worker pool is the template, → ~20 s), `detectBallLaunch` runs Vision at full
resolution with no downscale, and `renderTracerOnClip` re-encodes the whole
clip to draw an arc over the last ~1–2 s — splitting at `animStartSec`
(passthrough head, encode tail) cuts ~50–70% per clip. Note the trajectory
request is deliberately one stateful instance and must stay serial per clip.

## 6. Security-review hardening of the prefetch cache (follow-up)

The Claude security scan on the merged head found (MEDIUM) that the prefetch
cache's account hygiene was weaker than §3.4 claimed: `clearRoundPrefetch()`
was reachable only from the sign-out **button** and account deletion — a
session ending via remote revoke or refresh-token failure (the auth listener's
`SIGNED_OUT` branch) left the departing user's payloads in memory; untaken
entries were retained for the process lifetime (the TTL gated serving, not
retention); and a take was keyed on round id alone, so a cache hit skipped the
RLS check a live `getRound` would enforce.

All three closed in `lib/roundPrefetch.ts` + `hooks/useAuth.ts`:
entries are now stamped with the warming user's id and a take by any other (or
no) account resolves null → the consumer falls back to a live, RLS-enforced
fetch; `clearRoundPrefetch()` also runs in `resetLocalAccountState()` (every
`SIGNED_OUT`, button or not); and retention is bounded — expired entries are
swept on every prefetch/take and the cache drops on app-background. The
`localWipe.ts` comments now state the real retention bound.
